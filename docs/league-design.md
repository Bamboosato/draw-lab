- **対象:** Draw Lab連携プロジェクトのリーグ戦作成・運用機能
- **文書種別:** リーグ用新規設計書
- **バージョン:** 0.3.1（対応案No.1〜11、リーグ星取表PDF/印刷を確定）
- **作成日:** 2026-08-28
- **更新日:** 2026-08-31
- **要件正:** `docs/league-requirements.md`
- **UI参考:** `docs/screen-spec.md`
- **既存実装参考:** `src/components/AppShell.tsx`、`src/app/tournamentFlow.ts`、`src/components/ConfirmDialog.tsx`、`src/components/ValidationBanner.tsx`

本書は、リーグ要件を実装可能な構造へ分解する。既存トーナメントのドメインモデルは再利用せず、共通UI・保存基盤・画面遷移の考え方のみを再利用する。

## 1. 設計方針

### 1.1 基本方針

- リーグデータは`League`モデルとして独立させる。
- 参加者の登録と選出は同じ名簿入力画面で行い、グループ分け、対戦カード作成、結果入力、順位表示を段階的に分離する。
- 勝点・順位の計算は純粋関数として実装し、Reactコンポーネントから分離する。
- 星取表は閲覧用、結果入力は対戦カード一覧に限定する。
- グループ内の全組み合わせを候補カードとして作成し、有効／無効を運営者が選択する。
- 有効カード確定前は設定変更を許可し、確定後は設定を変更できない。確定解除時に結果入力済みの場合は、確認後にすべての結果をリセットする。
- 参加者名や試合結果を外部へ送信しないローカルファースト構成とする。

### 1.2 トーナメント機能との分離

| 項目 | トーナメント | リーグ |
|---|---|---|
| 主モデル | `Tournament` | `League` |
| 参加者 | `Entrant` | `LeagueParticipant` |
| 生成結果 | `GeneratedDraw` | `LeagueMatch[]` / `LeagueStanding[]` |
| 主要処理 | シード・BYE・配置 | 選出・グループ・候補カード・集計 |
| 保存領域 | `tournaments` object store | `leagues` object store |
| 主要画面 | 基本情報、名簿、オプション、プレビュー | 基本情報、名簿入力・選出、グループ・対戦、リーグ表 |

既存トーナメントの`TournamentProvider`、`Tournament`、`Entrant`、`GeneratedDraw`へリーグ固有のプロパティを追加しない。

### 1.3 対応案No.1〜11の確定方針

要件定義で確定した対応案を、次の設計方針として固定する。

- グループ内の全組み合わせを候補カードとして生成し、初期状態を全カード有効とする。必要なカードだけを無効化して対戦対象を調整する。
- MVPでは有効カードの試合順を手動変更せず、生成順を保持する。
- ダブルスはメンバー2名、チームはメンバー1名以上とし、チームの固定人数上限は設けない。
- 勝点は0〜100の整数、初期値は勝ち3・引き分け1・負け0とする。
- 手動順位は全参加単位へ順位番号を入力する。作業中の一部未入力は許可するが、`completed`遷移時は全順位を必須とする。
- 結果と備考は結果入力後も編集できる。リーグ表の参加者表示（ペア名・氏名を含む）は読み取り専用とし、参加単位・グループなどの構造変更は、対戦カード確定後は禁止する。
- 欠員発生時は名簿の選出チェックを変更する。対戦カード確定前は再構成を許可し、確定後は現在のリーグで禁止する。
- `completed`は読み取り専用とし、確認後に`inProgress`へ再開できる。結果・備考・順位・有効カード状態は保持する。
- リーグ一覧はトーナメント一覧と分離し、既存`AppShell`と共通UI・操作密度を利用する。
- リーグ表の星取表は、画面表示用UIと分離した専用印刷文書をブラウザ印刷へ渡す。対象は選択中グループだけとし、A4縦で8列単位にページ分割する。

## 3. ドメイン設計

### 3.1 Leagueのライフサイクル

```text
draft
  -> participantsReady
  -> selectionReady
  -> groupsReady
  -> scheduled
  -> inProgress
  -> completed
```

`League.status`は作業状態、`matchSelectionStatus`は候補カードの有効状態確定として別々に保持する。

```ts
type LeagueStatus = "draft" | "scheduled" | "inProgress" | "completed";
type MatchSelectionStatus = "pending" | "confirmed";
```

### 3.2 参加単位

```ts
type LeagueParticipant = {
  id: string;
  displayName: string;
  participantType: "individual" | "doubles" | "team";
  memberNames: string[];
  team?: string;
  region?: string;
  note?: string;
  selectionStatus: "selected" | "reserve" | "excluded";
};
```

- 対戦・勝敗・勝点の単位は常に`LeagueParticipant`とする。
- ダブルスやチームのメンバーごとの勝敗は保持しない。
- `participantType === "doubles"`の場合、`memberNames`は空欄でない2名でなければならない。
- `participantType === "team"`の場合、`memberNames`は空欄でない1名以上とし、固定の上限は設けない。
- `participantType === "individual"`の場合、表示名を1名の参加単位として扱う。
- 表示名ではなくIDでグループ、カード、順位を参照する。
- 同じ表示名の参加単位はIDによって区別する。

### 3.3 選出・補欠

```ts
type LeagueSelection = {
  mode: "all" | "random" | "manual";
  randomSeed?: string;
  selectedParticipantIds: string[];
  reserveParticipantIds: string[];
};
```

#### 抽選処理

1. 入力順と参加単位IDを正規化する。
2. `randomSeed`から再現可能な乱数列を作る。
3. 参加単位をシャッフルする。
4. 定員数を選出者、残りを補欠にする。
5. 選出結果と乱数シードを保存する。

#### 名簿画面での選出

- 選出は名簿一覧の最左列に配置したチェックボックスで手動指定する。
- チェックありを選出者、チェックなしを補欠として扱い、チェックなしの行全体（各セルと入力欄）を薄いグレーで表示する。
- `自動選出`ボタンは名簿画面の上部操作に配置し、`行追加`の左側に置く。
- `自動選出`を押すと既存のチェック状態をリセットし、入力済み参加者から定員分（定員未満の場合は全員）をランダムに選出する。
- 選出チェックの変更は、対戦カード確定前であれば許可する。既存のグループ・カードがある場合は影響確認後に再構成する。
- 対戦カード確定後は選出チェックボックスを無効化する。

### 3.4 グループ

```ts
type LeagueGroup = {
  id: string;
  name: string;
  participantIds: string[];
};
```

- 自動振り分けは、選出者をグループ人数差1以内になるよう配分する。
- 所属（`LeagueParticipant.team`）と地区（`LeagueParticipant.region`）が入力されている場合は、同じ属性値が同じグループへ集中しないよう、属性の重複数が少ないグループを優先する。
- 所属・地区の分散と人数均等を同時に満たせない場合は、人数差1以内を維持したうえで、所属・地区の重複数を最小化する。
- 属性の重複が同数の場合はグループ順と名簿上の順序で決定し、同じ入力で同じ結果を返す。
- 手動移動後は、各グループの人数と対戦可能数を再検証する。
- グループ分けの変更は、既存カードと結果へ影響するため変更確認を行う。

### 3.5 候補カード

```ts
type LeagueMatch = {
  id: string;
  groupId: string;
  order: number;
  participantAId: string;
  participantBId: string;
  isValid: boolean;
  result: "unplayed" | "participantAWin" | "draw" | "participantBWin";
  note?: string;
};
```

#### 候補カード生成

`generateCandidateMatches(groups)`は、方式にかかわらず各グループ内の全組合せを一度だけ生成する。

```text
グループA: A1, A2, A3, A4
  -> A1-A2, A1-A3, A1-A4, A2-A3, A2-A4, A3-A4
```

- カードはグループ順、グループ内は同じ参加単位（個人なら選手、チームならチーム）が連続しないよう可能な範囲で決定的に並べる。MVPではこの試合順を手動変更しない。
- 同一参加単位同士のカードは作らない。
- 同一組合せの重複カードは作らない。
- 生成した全カードを候補として扱い、初期状態では全カードを有効とする。
- 必要なカードだけを無効化して、グループ内の対戦対象を調整する。
- 各カードの初期`isValid`は`true`とする。

グループ内の参加単位数を`n`とした場合、候補カード数は`n × (n - 1) / 2`とする。候補カードの有効状態は対戦カード画面で調整し、参加単位ごとの有効試合数も同画面で確認できるようにする。

対戦順はラウンドロビン方式を基に、隣接するカードで参加単位が重ならない順序を優先する。参加単位数が少なく完全に分離できない場合は、全組み合わせを保持したうえで連続の発生を可能な範囲で最小化する。

#### 対戦カードの確定と確定解除

```text
候補カード生成
  -> isValidを選択
  -> 対戦カードを確定
  -> matchSelectionStatus = confirmed
  -> 有効カードのみを運用対象にする
  -> 確定解除まで設定変更不可
```

- 無効カードは削除せず保持する。
- 対戦カード確定前は`isValid`を切り替えられる。
- 対戦カード確定後は`isValid`を切り替えず、既存の有効状態と集計を保持する。
- 無効化しても結果・備考は削除しない。
- 無効カードは試合数、勝敗数、勝点の集計対象外とする。
- `isValid`変更でカード候補自体を再生成しない。

### 3.6 結果と勝点

```ts
type LeagueScoringPolicy = {
  winPoints: number;
  drawPoints: number;
  lossPoints: number;
};
```

各値は0〜100の整数とし、初期値は`winPoints: 3`、`drawPoints: 1`、`lossPoints: 0`とする。

`calculateStandings(matches, scoringPolicy)`は、`isValid === true`かつ結果が`unplayed`でないカードだけを入力として集計する。

```text
participantAWin -> AにwinPoints、BにlossPoints
draw            -> A/BにdrawPoints
participantBWin -> AにlossPoints、BにwinPoints
unplayed        -> 両者に加点しない
isValid=false   -> カード全体を集計しない
```

### 3.7 手動順位

- 勝点による自動表示値と手動順位を別々に保持する。
- 手動順位は同率者に限定せず、全参加単位を対象に指定できる。
- 表示層は自動順位、手動順位、順位未確定を区別する。
- 手動順位は各参加単位に順位番号を入力するUIとし、並べ替え操作だけに依存しない。
- 作業中は一部未入力を許可する。`completed`遷移時に重複・欠番・範囲外がない全順位を要求する。
- 結果変更後に手動順位を自動消去しない。
- 結果変更後は勝点と自動順位を再計算し、手動順位との不整合の可能性を警告する。

## 4. 変更影響と状態遷移

### 4.1 ChangeImpact

参加者、グループ、カード有効状態の変更を、保存前に影響情報へ変換する。

```ts
type ChangeImpact = {
  affectsGroups: boolean;
  affectsMatches: boolean;
  affectsResults: boolean;
  affectsStandings: boolean;
  messages: string[];
};
```

### 4.2 変更別の扱い

| 操作 | 対戦カード未確定 | 対戦カード確定済み |
|---|---|---|
| 有効カードを無効化 | 即時反映 | 操作不可 |
| 無効カードを有効化 | 即時反映 | 操作不可 |
| 結果・備考の編集 | リーグ表へ遷移不可 | 即時再集計 |
| 参加単位画面での情報更新 | グループ・候補カード・順位集計をリセットして再設定。既存設定がある場合は確認ダイアログを表示 | 禁止し、エラー表示 |
| リーグ表での参加者表示・備考の扱い | 参加者表示は読み取り専用、備考は即時反映 | 参加者表示は読み取り専用、備考は即時反映。結果の再集計と手動順位再確認を表示 |
| 参加単位の追加・削除 | グループ・候補カード・順位集計をリセットして再設定 | 禁止し、エラー表示 |
| グループ移動 | 未確定の候補カードがあれば再生成確認、確定済みの対戦カードがあれば未確定へ戻す再構成確認 | 禁止し、エラー表示 |
| 選出チェック変更 | グループ・カード影響確認 | 禁止し、エラー表示 |
| 対戦カードの確定解除 | 対象外 | 結果入力済みなら確認後に全結果をリセットし、未確定へ戻す |
| `completed`の再開 | 対象外 | 確認後に`inProgress`へ戻す |

参加単位・グループの変更と、カードの有効／無効切り替えは別の操作として扱う。

### 4.3 カード有効状態の操作制約

- 対戦カード確定前は、対戦カードの有効／無効を即時反映する。
- 対戦カード確定後は、対戦カードの有効／無効を変更できない。
- 確定解除時に結果入力済みカードが1件でもある場合は確認ダイアログを表示し、確認後にすべての結果を`unplayed`へリセットする。結果未入力の場合は確認なしで未確定へ戻す。

参加単位画面でグループまたは対戦カード設定が存在する状態の変更では、次を表示する。

- グループ分けと対戦カード設定がリセットされること
- 勝点設定は保持されること
- `リセットして反映`、`キャンセル`の操作

参加単位の各入力欄は編集中の値を行内に保持し、フォーカス離脱時に変更を確定する。確認ダイアログをキャンセルした場合は、その行の編集中の値を変更前へ戻す。貼り付けも同じ確認対象とし、キャンセル時は貼り付け内容を保持する。

`completed`中は、結果、備考、表示名、手動順位、有効カード状態を含むリーグデータを読み取り専用で表示する。再開時は`status`だけを`inProgress`へ戻し、上記データを保持する。

### 5.2 リーグ用ステッパー

既存のトーナメント用`stepper-band`、`stepper`、`stepper-item`のCSSと視覚状態を再利用する。

```text
1 基本情報
2 名簿入力・選出
3 グループ設定
4 対戦カード
5 リーグ表
```

- 現在ステップは`active`、完了済みは`complete`、未到達は`upcoming`とする。
- 5ステップを常に1行で表示し、標準幅では5列、狭い画面ではステッパー内部のみ横スクロールさせる。ページ全体の横スクロール・縦方向の表示崩れは発生させない。
- ステッパーはスマートフォンで横スクロール可能にする。
- 未完了の前提条件で後続画面へ直接アクセスした場合は、既存の`tournamentFlow`と同じく前提画面へリダイレクトする。
- View Transitions APIは既存の`viewTransitionNavigation`方針に合わせ、非対応ブラウザとモーション低減設定では通常遷移とする。

### 5.3 SCR-L-001 リーグ一覧

既存のトーナメント一覧と同じページ構造・操作密度を採用する。

- 共通のページ見出し、概要帯、表パネル、アクション領域を使用する。
- 一覧には大会名、種目、開催日、定員、状態、最終更新、アクションを表示する。大会名には会場を補助表示し、種目には種目名とシングル／ダブルス／チームの区分を表示する。
- 初期表示は最終更新の新しい順とし、開催日と最終更新の列見出しからトーナメント一覧と同じ昇順・降順を切り替えられるようにする。未設定・不正な日付は末尾へ表示する。
- 概要帯には全リーグ数、編集中数、運用中数、完了数をこの順で表示する。各項目はトーナメント一覧と同じ固定幅・左寄せとし、5列目は空欄とする。運用中は候補カード確定済みかつ未完了、完了は`completed`、編集中はそれ以外とする。スマートフォン幅ではトーナメント一覧と同じレスポンシブ表示へ切り替える。
- 一覧上部には`新規作成`とリーグ一覧のその他の操作メニューを配置する。その他の操作には、`全リーグバックアップ`と`リーグ情報の復元`を含める。
- 各行には`編集`、`リーグ表`、その他の操作メニューを配置し、その他の操作には`勝点設定`、`複製`、`出力`、`削除`を含める。`編集`は状態に応じて、未入力時は基本情報へ直接遷移し、複数ステップが保存済みの場合は編集画面メニューを表示する。完了済みはリーグ表を開き、そこから編集を再開する。`勝点設定`はダイアログで編集し、保存時に順位表を再集計する。
- 対戦カード未確定のリーグでは`リーグ表`を無効化し、表示できない理由をツールチップまたはARIAラベルで示す。
- `複製`は、基本情報、参加単位、選出・補欠、グループ、勝点設定を引き継いだ新規リーグを作成する。ただし、リーグIDおよび関連IDは再発行する。
- 複製後は候補カードを保持したまま`matchSelectionStatus = "pending"`に戻し、全候補カードを`isValid = true`で初期化する。結果は`unplayed`、備考は空欄、順位集計は0、手動順位は未指定とする。
- 複製元は変更せず、複製後のリーグは一覧から対戦カードを再確認・確定してからリーグ表へ進める。
- リーグ専用の一覧として構成し、トーナメント一覧と同一画面へ混在させない。
- 削除などの破壊的操作は既存の確認ダイアログを使用する。
- 一覧の保存中、読込中、保存エラーの表示方式をトーナメント一覧と統一する。
- 空状態では、リーグ作成への導線とリーグ機能の説明を表示する。

### 5.4 SCR-L-002 リーグ基本情報

既存の基本情報画面と同じカード、ラベル、入力欄、下部アクションのレイアウトを使用する。

- 大会名、開催日、会場、種目名、備考、種目区分を入力する。種目区分の選択肢はシングル、ダブルス、チームとする。
- 大会名はトーナメント基本情報と同じく任意とし、未入力でも次のステップへ進める。
- 大会名以外の必須項目のエラーは入力欄近傍と共通`ValidationBanner`の両方で識別できるようにする。
- 初期表示では必須エラーを表示せず、`次へ`操作後に表示する。フォーカス離脱だけでは表示しない。
- 基本情報画面では保存中表示を行わない。入力内容は自動保存し、保存失敗時のみエラーを表示する。
- `次へ`で参加単位画面へ遷移し、`一覧へ戻る`で一覧へ戻る。

### 5.5 SCR-L-003 名簿入力・選出

既存の名簿入力画面のテーブル構造と操作思想を参考にする。内部モデル・要件上の用語は`LeagueParticipant`（参加単位）とし、画面上は参加者を基本の表示名にする。

- 画面順は、上部操作、参加者入力概要、参加者一覧、TSV/CSV貼り付け、下部ナビゲーションとする。
- 名簿入力画面の初期表示では、定員と同数の空行を用意する。空行は入力済み参加者数・選出者数には算入しない。
- 上部操作は`自動選出`、`行追加`、`空行削除`、`入力チェック`とし、`自動選出`は`行追加`の左側に配置する。下部には`一覧`、`戻る`、`次へ`を配置する。
- `自動選出`を補助操作として提供し、通常は名簿一覧のチェックボックスで手動選出する。自動選出時は既存のチェック状態をリセットし、定員分をランダムに選択する。
- 名簿一覧の最左列に`選出`チェックボックスを配置する。チェックありを選出者、チェックなしを補欠とし、チェックなしの行全体（各セルと入力欄）を薄いグレーで表示する。
- 選出者と補欠を分けた別一覧は設けず、補欠からの繰り上げはチェックを付ける操作で行う。
- 一覧の見出し・件数表示は設けず、表パネルを直接表示する。表示名列は個人が`選手名`、ダブルスが`ペア名`、チームが`チーム名`とする。
- 参加者入力概要は`参加者数`、`選択済み`、`定員`の3項目を固定幅で左寄せに配置し、`選択済み`には現在チェックされている選出者数を表示する。入力チェック後にエラーがある場合だけ右端のサマリー領域へエラー文言を表示する。
- 表パネルの外側に追加の見出し・件数表示・カード枠を設けず、トーナメントの名簿入力画面と同じ表の見せ方とする。
- 貼り付け見出しは`TSV/CSV貼り付け`、取り込み操作は`貼り付けを取り込み`とする。
- 貼り付け列は実際の入力項目順とし、シングルは`選手名・所属・地区・備考`、ダブルスは`ペア名・選手名1・選手名2・所属・地区・備考`、チームは`チーム名・メンバー（/区切り）・所属・地区・備考`とする。既存の入力済み参加者を保持し、保存済みの空行へ順に取り込み、余った参加者を末尾へ追加する。
- 詳細列（地区・備考）は初期状態で閉じ、所属列右上の`⊕`／`⊖`で開閉する。閉じても入力値と保存データは削除しない。
- 列幅は`No.`約56px、表示名（選手名／ペア名／チーム名）約180px、メンバー約240px、所属約200px、地区約140px、備考約240px、操作約88pxを基準とする。詳細列を閉じた場合は見出しと各行セルを同時に非表示にし、狭い画面では表の横スクロールで入力欄を保持する。
- 初期表示およびフォーカス離脱だけでは入力エラーを表示せず、`入力チェック`または`次へ`操作後に参加者入力概要の右端セルへエラー文言を表示する。名簿入力画面では独立したエラーカードを挿入しない。

- Excelやスプレッドシートから貼り付けやすい行単位入力を採用する。
- 個別追加、行編集、行削除を提供する。
- 個人、ダブルス、チームで入力列を切り替える。
- ダブルスは必須のメンバー欄を2つ表示し、チームは1名以上を追加できる可変長のメンバー入力領域を表示する。
- ダブルスのメンバー数が2名でない場合、チームのメンバーが0名の場合は、行の確定または次段階への遷移を禁止する。
- 詳細列の開閉方式は既存名簿画面の考え方を再利用し、閉じても入力値を削除しない。
- 横幅が画面を超える場合は`.table-panel`内だけをスクロールさせる。
- グループまたは対戦カード設定が存在する状態で参加単位を追加・削除・更新・貼り付けする場合は、リセット確認ダイアログを表示する。確認前はリーグデータへ反映せず、キャンセル時は変更前の参加単位と編集中の入力値を維持する。
- 確認時は、グループ、候補カード、有効カード確定状態、順位集計をリセットし、勝点設定を保持する。

### 5.6 SCR-L-004 選出機能（名簿入力内）

- 選出状態は`LeagueParticipant.selectionStatus`と`LeagueSelection`のID配列で保持する。
- 名簿画面では定員、選出者数、入力エラーを確認できる。
- 選出者数が1名未満または定員超過の場合は、次のステップへ進めない。
- グループまたはカードが存在する状態で選出チェックを変更した場合は、リセット確認後に再構成する。
- 旧`/edit/selection`へのアクセスは、名簿入力・選出画面へリダイレクトする。

### 5.7 SCR-L-005 グループ設定

- グループ数指定と1グループ人数指定を切り替える。
- 自動均等振り分けボタンと、参加単位ごとのグループ変更ボタンを提供する。
- グループ内の全組み合わせを候補カードとして作成する。
- グループ数設定と自動均等振り分けはグループ一覧の上側に配置する。
- グループ設定は、グループ、No.、選手名、所属、地区、備考、操作の一覧で表示する。グループの昇順、グループ内は名簿入力と同じNo.の昇順とする。
- 地区と備考は、名簿入力画面と同じ詳細列の開閉操作で表示・非表示を切り替える。
- 勝点設定はリーグ一覧の各行にある`その他の操作`から開く。勝ち、分け、負けの勝点を0〜100の整数で入力し、初期値は3、1、0とする。結果入力済みの場合は保存時に順位表を再集計し、`completed`中は読み取り専用とする。
- グループ設定変更時は、対戦カード確定前は既存カードへの影響確認を表示し、確定後は拒否する。

### 5.8 SCR-L-006 対戦カード・有効カード確定

#### 対戦カード一覧

- グループタブごとに対戦カードを表示する。
- 試合順、参加単位A、参加単位B、有効／無効、結果状態を表示する。
- グループ内の全組み合わせによる対戦カード全件を表示する。
- 各カードに有効／無効のチェックボックスまたはスイッチを置き、初期状態は全カード有効とする。
- グループごとの対戦カード数、有効数、無効数、参加単位ごとの有効試合数を表示する。
- 参加単位ごとの有効試合数を表示する。
- `次へ`で有効カードを確認し、`matchSelectionStatus`を`confirmed`にしてリーグ表へ進む。
- 対戦カードの試合順は生成順で固定し、MVPでは手動変更を提供しない。

#### 確定と確定解除

- 確定前は有効／無効の変更を即時反映し、`対戦カードを確定`で確定状態へ進める。
- 確定済みでは有効／無効のチェックボックスと`対戦カードを再生成`を無効化し、`確定解除`を表示する。
- `確定解除`時に結果入力済みカードが1件でもある場合は`ConfirmDialog`を表示し、確認後にすべての結果を`unplayed`へリセットする。キャンセル時はカード状態、結果、確定状態を変更しない。
- 無効カードは一覧から消さず、視覚的に無効状態を示す。

### 5.9 SCR-L-007 リーグダッシュボード

```text
[ A ] [ B ] [ C ] ...

[対戦カード] [対戦結果]
```

- グループ選択を表示タブの上段に独立パネルとして配置し、A〜Dのひとまとまりのセグメントコントロールを表示する。選択中のグループは青背景・白文字で示し、グループ選択と表示タブの間に12〜16px程度の余白を設ける。
- 表示タブは`対戦カード`、`対戦結果`の順に並べ、現在の下線付きでブラウザのタブ切替えに近い見た目を維持する。
- 表示タブとコンテンツは同じパネル内に配置し、表示タブをコンテンツパネルの上端へ接続する。
- `対戦結果`には星取表と順位表をまとめ、星取表を上、順位表を下に表示する。
- 初期表示は`対戦カード`とする。
- 結果入力は対戦カード表示からのみ行う。
- 順位表は勝点、勝敗数、試合数、手動順位状態を表示する。
- 星取表と順位表の縦方向の参加者見出しは`参加者`とし、ダブルスは`ペア01（佐藤一郎 / 鈴木太郎）`のようにペア名と氏名を読み取り専用で表示する。星取表の横方向の列見出しはペア名だけを表示する。
- 手動順位は各参加単位へ順位番号を入力する。作業中は一部未入力を許可し、`completed`遷移時に全順位の入力を要求する。
- 順位未入力のエラーは初期表示では表示せず、`リーグを完了`押下時に表示する。
- 星取表は閲覧専用とし、結果セルは勝ちを`勝`、負けを`負`、引き分けを`分`、未実施を`未`、無効カードを`無`と表示して、無効カードが集計対象外であることを識別できるようにする。
- 対戦カード表示は有効カードを主対象とし、無効カードは必要に応じて表示切り替えできるようにする。
- 参加単位名、チーム名、メンバー名が長い場合は折り返しまたは省略表示する。
- `completed`中は読み取り専用とし、再開操作の確認後に`inProgress`へ戻す。
- グループ選択を上段、表示タブを下段に配置して分離する。
- 画面上部に対戦カード画面への重複導線は設けず、フッターに`戻る`（対戦カード画面）と`一覧`（リーグ一覧）を配置する。フッターの各ボタンには遷移先または操作内容のツールチップを付ける。

#### 星取表のPDF/印刷

- `リーグを完了`の右側に`PDF/印刷`を配置する。選択中グループの印刷対象がない場合（参加者0名、または17名以上）は無効にする。
- 押下時は`window.print()`を起動し、ブラウザの印刷先でPDF保存または印刷を行う。
- 印刷用DOMは画面用の星取表を流用せず、`LeagueMatrixPrintDocument`で専用生成する。画面用のタブ、サマリー、操作UI、サイドバーは印刷しない。
- `buildLeagueMatrixPrintPages`はグループ内参加者を名簿No.順に扱い、N=1〜8は1ページ、N=9〜16は先頭8列と残り列の2ページへ分割する。
- 印刷ページの各結果セルは、対角セルだけを`isDiagonal`で表現し、UI側のSVG線を左上から右下へ描画する。非対角セルは結果を持たない空欄とする。
- 印刷セルはA4縦の本文幅へ収め、手書き入力用に高さ14mm以上（9pt前後の3行分以上）を確保する。
- Nが9〜16の場合、2ページ目以降の結果列幅は1ページ目と同じ19.5mmとし、残り列が少ないページは右側に余白を残す。
- 印刷直前に既定ファイル名を`大会名_リーグ表-グループA`形式へ切り替え、印刷後は画面タイトルへ戻す。

### 5.10 SCR-L-008 リーグJSON復元

既存の大会情報復元画面と同じファイル選択、解析結果、エラー表示、確認操作を採用する。

- 個別リーグJSON（`kind: "draw-lab-league"`）か全リーグバックアップ（`kind: "draw-lab-league-backup"`）かをスキーマバージョンと種別で検証する。
- 個別リーグは既存リーグを上書きせず、新しいリーグIDおよび関連IDで追加する。
- 全リーグバックアップは、現在のリーグ件数、バックアップ件数、出力日時を表示し、確認後に現在の全リーグをバックアップ内容へ置き換える。
- 全リーグバックアップが0件の場合も置換復元を許可するが、現在の全リーグが削除されることを明示する。
- 全リーグバックアップの復元では、バックアップ内のリーグIDおよび関連IDを保持する。
- `isValid`、`matchSelectionStatus`、結果、備考、手動順位を復元する。
- 個別・全件のいずれも、解析・検証・保存に失敗した場合は既存データを変更しない。

## 6. 既存UIとの統一ルール

### 6.1 共通シェル

既存の`AppShell`をリーグルートにも適用する。

### 6.2 共通コンポーネントとCSS

以下は新規リーグ専用デザインを作らず、既存のコンポーネント・CSSを利用または汎用化する。

| 用途 | 再利用対象 |
|---|---|
| 確認 | `ConfirmDialog` |

### 6.3 レスポンシブ

- ページ全体の横スクロールは発生させない。
- 表形式の情報は、必要に応じて`.table-panel`内だけを横スクロールさせる。

- 結果入力ボタンはタップ可能な標準サイズを確保する。
- ボタンの意味を色だけで伝えず、ラベル、選択状態、ARIA属性で示す。

### 6.4 文言・アクセシビリティ

- 既存画面の「保存中」「保存済み」「保存に失敗しました」などの状態文言を統一する。
- エラーと警告は`role="alert"`または`role="status"`の適切な用途で通知する。
- タブは現在選択中の状態を`aria-selected`で示す。
- 有効／無効はチェック状態だけでなく、テキストでも示す。
- ダイアログを開いたときはフォーカスを管理し、キャンセル後は起点の操作へ戻す。
- キーボードだけで参加単位追加、カード有効切り替え、結果入力、順位操作を完了できるようにする。

## 7. 保存・JSON設計

### 7.1 IndexedDB

- 既存の`draw-lab`データベースを使用する。
- DBバージョンを上げ、新しい`leagues` object storeを追加する。
- `tournaments` object storeは変更せず、既存データをそのまま読み書きできるようにする。
- `LeagueRepository`は`list`、`get`、`put`、`delete`を提供する。
- 保存状態は`loading`、`ready`、`saving`、`error`を既存Providerと同じ考え方で扱う。
- 保存失敗時は画面の入力状態を維持し、再試行できるようにする。

### 7.2 LeagueProvider

`LeagueProvider`はリーグ一覧、選択中リーグ、作成、更新、削除、複製、個別追加、全件置換、保存状態を管理する。

- `TournamentProvider`と同じProviderへ混在させない。
- `useLeague(id)`と`useLeagues()`を提供する。
- 画面更新は不変更新で行う。
- `hasLeagueContentChanged`相当の判定で更新日時を管理する。
- 変更後の保存処理が競合した場合、最新の入力を失わない。
- 全件置換前に未実行の遅延保存を破棄し、復元データの後へ古い入力が書き戻されないようにする。

### 7.3 JSON

```ts
type LeagueJsonEnvelope = {
  kind: "draw-lab-league";
  schemaVersion: number;
  league: League;
};

type LeagueBackupJsonEnvelope = {
  kind: "draw-lab-league-backup";
  schemaVersion: number;
  exportedAt: string;
  leagues: League[];
};
```

- JSON変換は`leagueJson.ts`へ分離する。
- 個別出力は`draw-lab-league`、全件出力は`draw-lab-league-backup`として識別する。
- 全件出力ファイル名は`drawlab_league_backup_日時.json`とする。
- エクスポートは候補カード、`isValid`、確定状態、結果、備考、手動順位を含む。
- 個別インポート時はリーグID、参加単位ID、グループID、対戦カードIDを再採番する。
- 全件復元時はバックアップ内のIDを保持し、既存リーグを全置換する。
- 再採番後もすべての参照を整合させる。
- 不正なJSONを保存処理へ渡さない。

## 8. 要件トレーサビリティ

## 9. テスト設計

### 9.1 先行するテスト観点

実装前に、機能・非機能・データ・UIの観点を列挙し、正常系、異常系、境界値、状態遷移に分けてケース化する。

### 9.2 ドメイン単体テスト

#### 候補カード・有効状態

- 所属・地区が同一の参加単位を含む場合、自動振り分けで属性の重複が少ないグループを優先する意図を検証する。
- 所属・地区の完全分散が不可能な場合も、全参加単位が保持され、グループ人数差1以内になる意図を検証する。
- 同じ入力とグループ数で自動振り分け結果が再現される意図を検証する。
- グループ内の全組合せが1回ずつ候補カードとして生成される意図を検証する。
- 候補カードが全件有効で初期化され、生成順が再現される意図を検証する。
- 5参加単位以上では、隣接カードで同じ参加単位が連続しない順序になる意図を検証する。
- 参加単位数が少なく完全分離できない場合も、全組み合わせを保持し連続を可能な範囲で抑える意図を検証する。
- 4参加単位の候補カード数が6件になる意図を検証する。
- 有効／無効を切り替えると、参加単位ごとの有効試合数へ反映される意図を検証する。
- 有効カード数を減らしても候補カード自体が削除されないことを検証する。
- 確定前は有効／無効を変更でき、確定後は変更できないことを検証する。
- 確定解除時に結果入力済みなら確認後に全結果がリセットされ、未確定へ戻ることを検証する。
- 同じカードを重複生成しないことを検証する。

#### 参加単位・選出

- ダブルスのメンバー数が2名以外の場合にバリデーションエラーとなる意図を検証する。
- チームのメンバー数が0名の場合にバリデーションエラーとなり、1名以上では通過する意図を検証する。
- 対戦カード確定前に参加単位を追加・削除・更新すると、グループ、候補カード、有効カード確定状態、順位集計がリセットされ、勝点設定が保持される意図を検証する。
- 定員内の初期参加者が選出者としてチェック済みになる意図を検証する。
- チェックを外した参加者が補欠となり、チェックを付け直すと選出者へ戻る意図を検証する。
- `自動選出`が既存のチェック状態をリセットし、定員分を再選出して乱数シードを保存する意図を検証する。
- 対戦カード確定前に選出チェックを変更すると、グループ、候補カード、有効カード確定状態、順位集計がリセットされる意図を検証する。
- 対戦カード確定後の選出チェック変更が拒否され、既存データが変更されない意図を検証する。

#### 集計・順位

- 勝点設定が勝・分・負へ正しく適用される意図を検証する。
- リーグ一覧の各行のその他の操作から勝点設定を開き、保存できる意図を検証する。
- 勝点の初期値3・1・0、境界値0・100、範囲外・非整数入力を検証する。
- 未実施カードと無効カードが加点されないことを検証する。
- 結果変更・クリアで集計が再計算されることを検証する。
- 全参加単位に手動順位を設定できることを検証する。
- 同率でない参加単位を含めて順位番号を入力でき、作業中の一部未入力を許容する意図を検証する。
- `completed`遷移時に全順位の重複・欠番・範囲外を拒否する意図を検証する。
- 結果変更で勝点を再計算し、手動順位を保持したまま再確認を促す意図を検証する。

#### 状態制御

- 対戦カード確定後の結果・備考編集を許可し、リーグ表の参加者表示を読み取り専用としたうえで、参加単位の追加・削除、グループ変更を拒否する意図を検証する。
- `completed`中の編集を拒否し、確認後の`inProgress`再開で結果、備考、手動順位、有効カード状態を保持する意図を検証する。

### 9.3 UI・E2Eテスト

- 前提未完了のURL直接アクセスが適切な画面へ戻ること。
- 候補カード生成、カード有効切り替え、確定、確定解除後の再編集の一連の状態遷移。
- 既存のグループまたは対戦カードがある名簿入力・選出画面で、フォーカス離脱時の参加者変更と選出チェック変更に確認ダイアログが表示され、キャンセルで変更前の状態が維持され、確認でリセットが反映されること。
- 名簿一覧の最左列のチェックボックスで選出者と補欠を切り替えられ、補欠表示が参加者名の後ろに表示されること。
- `自動選出`が`行追加`の左側にあり、手動で選択済みの場合も押下で定員分の選出へ置き換わること。
- 対戦カード確定後は有効／無効のチェックボックスが無効化され、確定解除で結果入力済みの場合に確認ダイアログが表示されること。
- 対戦カード確定後に結果・備考を編集でき、リーグ表の参加者表示が読み取り専用で、参加単位追加・削除、選出チェック、グループ変更が操作できないこと。
- `completed`中の読み取り専用表示と、再開確認後に`inProgress`へ戻ること。
- 上段のグループ選択と下段の表示タブの切り替え。
- スマートフォンでカード操作と表の横スクロールが可能であること。
- リーグ一覧がトーナメント一覧と分離され、共通`AppShell`・既存UI部品で表示されること。
- リーグ一覧の列、開催日・最終更新の並び替え、上部追加アクション、行のその他の操作がトーナメント一覧と同じ操作密度であること。
- 個別リーグの追加復元と、確認付き全リーグ置換復元が一覧から実行できること。
- 保存中・保存失敗・再試行の表示。

### 9.4 実施範囲

リーグ画面を実装する段階では、まず対象画面・ドメインの単体テストと主要な状態遷移E2Eを実施する。全件E2Eやクロスブラウザー試験は、共通`AppShell`・保存処理・レスポンシブCSSへ変更が及ぶ場合に拡大する。

同一実機へのテストスクリプト並列実行は行わない。失敗時は入力データ、操作順、ブラウザ、画面幅、保存状態、コンソールログを記録する。

## 10. 実装順序

1. `leagueTypes.ts`とJSONスキーマを確定する。
2. 正規化・バリデーションを実装する。
3. 自動選出、名簿上の選出チェック、グループ分けを実装する。
4. グループ内全組み合わせの候補カード生成を実装する。
5. `isValid`切り替え、候補カード確定、変更影響計算を実装する。
6. 勝点集計、順位表、手動順位を実装する。
7. `LeagueRepository`とDBマイグレーションを実装する。
8. 個別／全件JSONエクスポート・インポートと全件置換を実装する。
9. 共通ステッパー・共通画面要素を汎用化し、リーグルートを追加する。
10. 各リーグ画面とダッシュボードを実装する。
11. 単体テスト、UIテスト、対象範囲を絞ったE2Eを実施する。
