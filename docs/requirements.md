# draw-lab 要件定義書

作成日: 2026-07-02  
更新日: 2026-09-03
対象: WEB版トーナメント表作成アプリ PoC（正式リリース版 1.0.0）
リポジトリ: `Bamboosato/draw-lab`

---

## 1. 概要

`draw-lab` は、テニス大会・サークル大会などで使用するトーナメント表を、WEBブラウザ上で作成するためのPoCアプリケーションである。

既存のExcel VBAトーナメント表作成アプリの仕様・操作思想を参考にしつつ、VBAコードやExcel固有の実装には依存しない。WEBアプリとして、名簿入力、シード配置、BYE補完、所属チーム・地区の偏りを考慮したドロー作成、画面プレビュー、PDF出力を独自に実装する。

---

## 2. 目的

本PoCの目的は以下とする。

- 参加者名簿からトーナメント表を自動生成できること
- シングルス・ダブルスの両方に対応できること
- シード、BYE、所属チーム、地区を考慮した配置ができること
- 生成したトーナメント表をWEB画面上で確認できること
- 対戦カードへ勝敗と備考を入力し、勝ち上がりをトーナメント表へ反映できること
- ブラウザ印刷またはPDF保存により、配布用のトーナメント表を作成できること
- 将来的なクラウド保存、共有URL発行、詳細スコア管理へ拡張しやすい構造にすること

---

## 3. 基本方針

最初のPoCでは、既存VBAアプリの全機能再現は目指さない。

優先するのは、以下の最小実用フローである。

```text
名簿入力
  ↓
入力チェック
  ↓
シード・BYE・所属偏りを考慮した配置
  ↓
トーナメント表生成
  ↓
対戦カードで勝敗入力
  ↓
勝ち上がりを反映したトーナメント表
  ↓
トーナメントを完了
  ↓
ローカル保存 / JSON出力 / PDF出力
```

WEB版では、Excelのセル結合・罫線・リボンUI・隠しシート設定などは移植しない。トーナメント生成ロジックと描画ロジックを分離し、将来的な拡張に耐えられる設計とする。

---

## 4. 想定ユーザー

主なユーザーは、大会やサークルイベントの運営者とする。

想定利用シーンは以下。

- テニス大会のドロー作成
- サークル内大会の組み合わせ作成
- 少人数〜中規模イベントのトーナメント表作成
- 作成したトーナメント表のPDF配布
- 紙に印刷して掲示・配布するための表作成

---

## 5. 対象環境

PoCでは、PCブラウザでの利用を主対象とする。

優先対象は以下。

- Google Chrome 最新版
- Microsoft Edge 最新版
- Windows / macOS のデスクトップ環境

スマートフォンは、閲覧や簡易確認は考慮する。ただし、名簿入力・編集の主対象にはしない。

PWAとしての正規配信元は以下とする。

```text
https://draw-lab.bamboosato.com/
```

ブラウザ保存データはOrigin単位で分離されるため、本番利用、PWAインストール、更新確認、サポート案内では上記Originを正規URLとして扱う。別のホスティングURLやlocalhostの保存データを本番Originへ自動移行・同期する機能はPoC対象外とし、必要な移行は既存のJSONバックアップ / インポートを使用する。

同一ページ内の画面遷移には View Transitions API を使用し、サイドバーなどの共通領域を維持したまま本文領域を短時間で切り替える。View Transitions API に未対応のブラウザではアニメーションを行わず、通常の画面遷移を継続する。OSまたはブラウザでモーション低減が指定されている場合もアニメーションを行わない。

## 7. 機能要件

## 7.1 トーナメント基本情報入力

ユーザーは、新規トーナメント作成時に以下の情報を入力できる。

| 項目 | 内容 | 必須 |
|---|---|---|
| 大会名 | トーナメント表に表示する大会名 | 任意 |
| 開催日 | 大会開催日 | 任意 |
| 会場 | 会場名 | 任意 |
| 種目名 | 男子シングルス、女子ダブルスなど | 任意 |
| 種目区分 | シングルス / ダブルス / チーム | 必須 |
| ドローサイズ | 4, 8, 16, 32, 64, 128 | 必須 |
| シード数 | 0（シードなし）, 2, 4, 8, 16など | 必須 |

PoCでは、ドローサイズは最大128までを対象とする。

---

## 7.2 名簿入力

ユーザーは、参加者を一覧形式で入力できる。

### シングルスの場合

| 項目 | 内容 | 必須 |
|---|---|---|
| No | 表示順または入力順 | 任意 |
| シード番号 | シード選手の場合に指定 | 任意 |
| 選手名 | 参加者名 | 必須 |
| 所属チーム | クラブ名、学校名、所属など | 任意 |
| 地区 | 地域、ブロック、所属地区など | 任意 |
| ランキング | シード候補確認用の順位。入力時は1〜9999の整数 | 任意 |

### ダブルスの場合

| 項目 | 内容 | 必須 |
|---|---|---|
| No | 表示順または入力順 | 任意 |
| シード番号 | シードペアの場合に指定 | 任意 |
| 選手名1 | ペアの1人目 | 必須 |
| 選手名2 | ペアの2人目 | 必須 |
| 所属チーム1 | 選手1の所属 | 任意 |
| 所属チーム2 | 選手2の所属 | 任意 |
| 同チーム扱い | 同一チーム扱いにする短いグループ文字列（1〜5文字） | 任意 |
| 地区 | ペアの地区 | 任意 |
| ランキング | シード候補確認用の順位。入力時は1〜9999の整数 | 任意 |

### チームの場合

チームはトーナメント表上の1ドロー枠として扱う。試合結果や勝ち上がりはチーム単位で扱い、メンバー単位では管理しない。

| 項目 | 内容 | 必須 |
|---|---|---|
| No | 表示順または入力順 | 任意 |
| シード番号 | シードチームの場合に指定 | 任意 |
| チーム名 | ドロー上に表示するチーム名 | 必須 |
| メンバー | チームに所属するメンバー。1名以上、人数上限なし | 必須 |
| 所属チーム | 同じ所属を避けるためのグルーピング情報 | 任意 |
| 地区 | チームの地区 | 任意 |
| ランキング | シード候補確認用の順位。入力時は1〜9999の整数 | 任意 |

チーム名の重複は許可する。チームはチーム名ではなく内部IDで識別するため、同名のチームも別参加単位として扱う。メンバー名の重複検査は行わない。

### 入力方式

PoCでは以下の入力方式に対応する。

- 画面上のテーブルへの直接入力
- ExcelやGoogleスプレッドシートからのコピー＆ペースト
- CSV形式テキストの貼り付け
- JSONインポートによる復元

Excelファイルの直接読み込みはPoCでは対象外とする。

## 7.3 名簿バリデーション

トーナメント生成前に、以下のチェックを行う。

名簿の全入力項目が空の完全空行は `Tournament.entrants` に保持し、保存時には削除しない。完全空行は検証・生成時だけ対象から除外し、有効参加者数およびBYE数の計算にも含めない。完全空行はBYEの明示指定を表すものではなく、BYEは有効参加者数とドローサイズの差から自動算出する。

名簿入力画面は、ドローサイズ分の行と、ドローサイズを超えて入力が存在する最後の行までを表示する。保存済みの末尾余剰完全空行は画面上で隠すが、`Tournament.entrants` からは削除しない。

選手名が空でも、シード番号、所属チーム、地区、ランキングなど、いずれかの項目に入力がある行は不完全行として検証対象に含め、従来どおり必須項目エラーとする。

| チェック項目 | 内容 | 種別 |
|---|---|---|
| 必須項目 | 完全空行を除き、選手名が未入力でないこと | エラー |
| ドローサイズ | 参加者数がドローサイズ以下であること | エラー |
| シード番号 | 数値として解釈できること | エラー |
| シード数 | 指定シード数がドローサイズを超えないこと | エラー |
| ランキング | 入力時は1〜9999の整数であること | エラー |

名簿入力概要では、有効参加者数がドローサイズを超えた場合、有効参加者数を赤色の警告表示にする。この場合のエラー対象は有効参加者数とし、算出できないBYE数は「不正」ではなく「—」と表示する。警告の詳細はツールチップで表示する。

基本情報のシード数と名簿のシード指定人数が一致しない場合は、名簿入力概要の「シード指定」を赤色の警告表示にし、指定人数へ「不足」または「超過」を付記する。警告の詳細はツールチップで表示し、両者が一致すると通常表示へ戻す。
| シード重複 | 同順位シード以外の不自然な重複を警告 | 警告 |
| 選手名重複 | 同一選手名の重複を警告 | 警告 |
| ダブルス入力 | 完全空行を除き、選手名1・選手名2が未入力でないこと | エラー |

エラーの場合は生成を止める。警告の場合は、内容を表示したうえで生成可能とする。

## 7.4 BYE処理

参加者数がドローサイズに満たない場合、空き枠をBYEとして自動補完する。

例:

```text
参加者数: 13
ドローサイズ: 16
BYE数: 3
```

PoCでは以下のルールを採用する。

- シード選手がいる場合、上位シード側にBYEを優先配置する
- シード選手がいない場合、全体のバランスを見てBYEを分散配置する
- BYE同士が初戦で対戦する配置は避ける
- BYEは選手ではなく、スロット状態として扱う

---

## 7.5 シード配置

ユーザーは、参加者ごとにシード番号を指定できる。

PoCでは以下に対応する。

- 第1シード
- 第2シード
- 第3〜第4シード
- 第5〜第8シード
- 第9〜第16シード
- 同順位シード

同順位シードの例:

```text
1, 1, 3, 4, 5, 5, 7, 8
```

同順位シードがある場合は、該当するシード枠の範囲内でランダム配置する。

基本方針は以下。

- 第1シードは上側の山に配置する
- 第2シードは下側の山に配置する
- 第3・第4シードは準決勝ブロックに分散する
- 第5〜第8シードは準々決勝ブロックに分散する
- それ以降のシードも、同一ブロックに偏らないよう配置する

競技団体ルールへの厳密な完全準拠は、PoCでは対象外とする。

---

## 7.6 ノーシード選手の配置

シード配置後、ノーシード選手を空き枠に配置する。

PoCでは、完全ランダムではなく、以下を考慮する。

- 同じ所属チームの選手が初戦で当たりにくいこと
- 同じ所属チームの選手が同じ山に偏りすぎないこと
- 同じ地区の選手が初戦で当たりにくいこと
- 同じ地区の選手が同じ山に偏りすぎないこと
- 条件が同等の場合はランダムに配置すること

配置ロジックは、候補枠ごとにペナルティスコアを計算し、スコアが低い枠を優先する方式とする。

ペナルティ例:

| 条件 | ペナルティ |
|---|---|
| 同チーム初戦対戦 | 大 |
| 同地区初戦対戦 | 中 |
| 同チームが同じ山に集中 | 小〜中 |
| 同地区が同じ山に集中 | 小〜中 |

同点の場合は乱数で決定する。

---

## 7.7 乱数シード

トーナメント生成時に乱数シードを保持する。

目的は以下。

- 同じ入力条件で同じ結果を再現できるようにする
- 不具合調査をしやすくする
- 生成結果の監査性を高める

ユーザーには通常表示しなくてもよい。ただし、開発・検証用には確認できるようにする。

---

## 7.8 トーナメント表プレビュー

生成したトーナメント表を画面上に表示する。

PoCでは、HTMLテーブルよりもSVGベースの描画を優先する。

理由は以下。

- トーナメント線を正確に描画しやすい
- 拡大縮小しても崩れにくい
- PDF出力に流用しやすい
- Excelのセル結合表現に依存しない

プレビューに表示する情報は以下。

- 大会名
- 開催日
- 会場
- 種目名
- 選手名
- 所属チーム
- シード番号
- BYE
- トーナメント線

ダブルスでは、選手名1・選手名2を縦並びに表示し、対応する所属チーム1・所属チーム2を選手名の右側に表示する。同チーム扱いの場合は、同じチーム名を重複表示せず1回だけ表示する。

地区はトーナメント表には表示せず、所属チーム・地区の偏り回避ロジックでのみ使用する。両山では左山・右山ともにドロー番号を上から昇順で表示する。途中ラウンドの「勝者 M…」カード、上部のラウンド見出し、「優勝」カードは表示しない。各段の接続線の横幅は、1回戦の出場者カード端から最初の縦線までの横線と同じ長さにする。両山の中央は、左右の最終線を同じ長さで接続し、中央から上へ線を出す逆T字で表示する。

試合結果の詳細、スコア、備考はトーナメント表には表示しない。結果の詳細は対戦カードの備考欄だけに保持する。

明示的な再生成操作は対戦カード画面に配置し、画面の「対戦カード」見出しと同じ行の右端に「1回戦の組合せを再生成」ボタンを表示する。この操作は新しい乱数シードでドロー全体を再生成するため、1回戦の組合せだけでなく、参加者の配置、シード・BYEの配置、以降の対戦経路も変わる可能性がある。結果または備考が1件でも入力された場合は、データ消失防止のためボタンを無効にする。無効時は「結果または備考入力済みのため、1回戦の組合せを再生成できません。」をツールチップで案内する。

## 7.8.1 トーナメントの勝敗入力

トーナメントにおいて、対戦カードへ勝敗を入力し、勝ち上がりをトーナメント表へ反映する。

対戦カード画面は、オプション設定画面とトーナメント表画面の間に配置する。ラウンドごとにタブを表示し、初期表示では1回戦を選択して、1回戦の全対戦カードを表示する。タブの補助ラベルは「ラウンド」とし、最終ラウンドのタブ名は「決勝」とする。カード一覧の見出しはラウンド名を含めず「対戦カード」とする。

各回戦のカードは以下の状態を持つ。

- 1回戦は生成済みのドロー枠から対戦者を表示する
- 2回戦以降は、前回戦の勝者が確定したカードから対戦者を表示する
- 対戦者が未確定のカードは、カードの枠と未確定状態だけを表示する
- BYE対戦は自動的に勝ち上がり、手動の勝敗入力は行わない
- 実際の対戦ではA側・B側の対戦者名を勝者選択ボタンとして表示し、押下した側を勝者として保存する。選択中のボタンを再度押下すると「未実施」に戻り、反対側を押下すると勝者を切り替える
- 「引き分け」は小さいボタンで表示するが、トーナメントでは無効色の無効状態とする。トーナメントで保存できる結果は「未実施」「participantAWin」「participantBWin」のみとする
- 結果入力済みのカードはステータスを「実施済」と表示し、青色のバッジで示す。対戦者が未確定のカードはステータスを「未確定」と表示する
- 試合番号はカード左上に見出しバッジとして表示し、薄い青色の背景、濃い青色の文字、左側のアクセント線、太字で識別しやすくする。試合番号の識別は色だけに依存しないこと
- 対戦カードには備考欄を設ける。備考はカードに保存するが、トーナメント表には表示しない

勝敗が入力された場合は、次回戦以降の対戦者を自動更新する。前回戦の結果変更により後続カードの対戦者が変わった場合、そのカードの結果と旧対戦者に紐づく備考を未入力へ戻す。

トーナメント表では、勝ち上がっている参加者の経路を濃いオレンジ色（`#c2410c`）かつ通常より少し太い線で表示する。勝者線は参加者側の横線、回戦の縦線、次回戦側の横線を連続して強調する。決勝の勝者が確定した場合は、優勝の縦線の上に優勝者のNo.を同じ濃いオレンジ色・少し太字で表示する。No.はドロー上の参加者番号（`DrawSlot.position`）とする。

結果・備考は生成入力署名には含めない。大会名などの表示情報や出力形式の変更では結果を破棄しない。シード、参加者、配置方式など生成結果に影響する入力を変更してドローを再生成する場合は、結果と備考をリセットする。入力済み結果がある場合は、リセット前に確認できること。

## 7.8.2 トーナメント完了と編集再開

トーナメント表画面では、`PDF/印刷`の左側に`トーナメントを完了`ボタンを配置する。生成済みドローが存在する場合は、試合結果の入力状況にかかわらず完了操作を実行でき、`Tournament.status`を`completed`へ変更して保存する。生成済みドローがない場合は完了せず、理由を画面内のエラー表示で案内する。

完了済みトーナメントは、一覧・ホームで状態を`完了`と表示する。完了済みのトーナメント表画面は読み取り専用とし、対戦結果、備考、組合せ、基本情報、名簿、オプションを変更できない。完了済みデータの編集導線はトーナメント表画面へ統一する。

完了済みトーナメント表画面では、`PDF/印刷`の左側に`編集を再開`ボタンを表示する。押下時は確認ダイアログを表示し、確認後に`Tournament.status`を`inProgress`へ戻す。編集再開時は結果、備考、組合せ、乱数シードを保持し、対戦カード画面を含む編集導線を再び利用可能にする。キャンセル時は完了状態と保存データを変更しない。

## 7.9 ローカル保存

PoCでは、ブラウザ内の正式なデータ保存先をIndexedDBとする。

保存方針は以下とする。

- 全大会を同一のIndexedDBデータベースで管理する
- 大会ごとに個別に取得、追加、更新、複製、削除できる構造とする
- 一覧表示に必要な複数大会を、ブラウザ再起動後も復元できること
- UIからIndexedDBを直接操作せず、保存層のインターフェースを経由する
- localStorageは正式な保存先として使用しない
- 既存バージョンのlocalStorageに大会データがある場合は、初回起動時にIndexedDBへ移行する
- 移行元データは、全件の検証とIndexedDBへの保存が成功するまで削除または上書きしない
- 読み込み、保存、移行に失敗した場合は、保存済み大会が0件であるかのように扱わず、ユーザーへエラーを通知する
- OPFSは本PoCの大会データ保存には使用せず、将来大容量データを扱う必要が生じた場合に再検討する

保存対象は以下。

| データ | 内容 |
|---|---|
| トーナメント基本情報 | 大会名、開催日、会場、種目名 |
| 名簿 | 参加者一覧 |
| 生成オプション | ドローサイズ、シード数、配置条件 |
| 出力形式オプション | 生成済みドローの表示・印刷レイアウト |
| 生成結果 | 各参加者の配置枠、回戦ごとの対戦カード、勝敗・備考、生成時入力署名 |
| 乱数シード | 再現用 |
| 状態 | `inProgress` または `completed` |
| 更新日時 | 一覧表示用 |

更新日時は、大会名、名簿、各種オプション、生成結果などの保存対象データに実質的な変更があった場合だけ更新する。入力内容を変更せずに「次へ」「戻る」で画面遷移した場合は更新しない。

生成済みドローには、生成結果へ影響する入力から作成した決定的な「生成時入力署名」を保存し、初回生成後の自動再生成が必要かを判定する。

- 署名対象は、種目区分、ドローサイズ、シード数、完全空行を除く名簿、生成オプション、乱数シードとする
- 大会名、開催日、会場、種目名などの表示情報と出力形式オプションは署名対象外とする
- 初回生成前は自動生成せず、オプション設定画面の「次へ」で初回生成する
- 初回生成時に採用した乱数シードは生成オプションへ保存し、初回生成後の自動再生成に使用する
- 初回生成後に署名対象を変更した場合は、保存した乱数シードを使って自動再生成し「生成済み」を維持する
- 名簿入力にエラーがある場合は生成済みドローを破棄して「未生成」とする。ただし保存した乱数シードは保持し、入力を修正して有効な状態へ戻した場合は自動再生成して「生成済み」へ戻す
- 初回生成後は、参加者行の削除を含め、ユーザーによる明示的な再生成を必須とするタイミングを設けない
- 完全空行の追加・削除だけでは自動再生成しない
- 既存データとの互換性のため、生成時入力署名がない生成済みドローは読み込み時点では有効とみなし、最初の編集時に編集前の入力から署名を補完する

## 7.10 JSONエクスポート / インポート

PoCでは、クラウド保存の代替としてJSONエクスポート / インポートに対応する。

目的は以下。

- 作成データをバックアップできる
- 別PCへデータを移せる
- 不具合調査時にデータを共有できる
- 将来的なクラウド保存設計に流用できる

JSONは、以下の2種類を扱う。

| 種類 | 用途 | 対象 |
|---|---|---|
| 個別大会JSON | 1大会の共有、複製、不具合調査 | 選択した1大会 |
| 全大会バックアップJSON | PC移行、ブラウザ移行、一括バックアップ | IndexedDBに保存されている全大会 |

個別大会JSONのインポートは、既存データを保持したまま新しい大会として追加する。大会IDを再採番する場合は、生成済みドローなどが保持する関連IDも整合するよう更新する。

全大会バックアップJSONは、少なくとも以下の形式とする。

```ts
type TournamentBackup = {
  schemaVersion: 1;
  exportedAt: string;
  tournaments: Tournament[];
};
```

各大会のJSONには、以下を含める。

- トーナメント基本情報
- 名簿
- 生成オプション
- 出力形式オプション
- 生成済みドロー
- 回戦ごとの対戦カード、勝敗、備考
- 生成時入力署名
- 乱数シード
- 作成日時・更新日時
- 大会ID、参加者ID、生成済みドロー内の関連ID

個別大会インポートでは、対戦カードが保持する生成済みドローIDおよび前回戦カードへの参照も新しいIDへ対応付ける。旧形式JSONに対戦カードがない場合は、配置枠から未実施状態の対戦カードを補完する。

全大会バックアップJSONの復元は、現在のIndexedDBに保存されている全大会をバックアップ内容で置き換える「全置換」を基本とする。初期PoCでは、既存大会を残したままバックアップを統合するマージ復元は必須としない。

一般ユーザー向けの復元画面名は「大会情報の復元」とする。復元はDrawLabから出力したファイルの選択に限定し、JSONテキストの直接入力機能は提供しない。ファイル内のJSON本文は画面に表示せず、読込後はデータ種別、対象件数、大会名など、復元判断に必要な要約だけを表示する。ファイルはクリック、タップ、ドラッグ＆ドロップで選択でき、選択直後に既存の検証・解析処理を自動開始する。処理中は二重実行を防止し、ファイル名と読み込み中・処理中・完了・エラーの状態を表示する。処理完了後は別のファイルおよび同一ファイルを再選択できるものとする。サンプルデータはJSON本文を表示せず、ファイル選択より控えめな補助操作から内部読込し、自動的に同じ解析処理を開始する。

全置換復元は、以下の順序で行う。

1. JSONを解析する
2. `schemaVersion` と全大会のデータ構造を検証する
3. 復元対象の大会数と、現在の全大会が削除されることを表示する
4. ユーザーの明示的な確認を得る
5. 1つのトランザクションで現在の全大会を削除し、バックアップ内の全大会を保存する
6. 復元結果を再読込し、件数と主要データを確認する

全大会バックアップの復元では、大会ID、参加者ID、生成済みドローのIDと参照関係を保持する。JSONの解析、検証、保存、再読込確認のいずれかに失敗した場合は、復元前のIndexedDBデータを保持し、全置換を完了扱いにしない。

バックアップファイルには全参加者の氏名、所属、地区等が含まれるため、エクスポート時と復元時に個人情報を含むことを明示する。

## 7.11 PDF出力

PoCでは、ブラウザ印刷機能を使ったPDF保存を基本とする。

実装方針は以下。

- トーナメント表をSVGまたは印刷向けHTMLで描画する
- `@media print` により印刷用CSSを適用する
- ブラウザの「PDFに保存」を利用する

PoCで対応するPDF出力項目は以下。

| 項目 | 内容 |
|---|---|
| 用紙サイズ | A4を基本 |
| 向き | 縦向きを基本 |
| 余白 | 印刷時に見切れない余白を確保 |
| 表示内容 | 大会名、開催日、会場、種目名、選手名、チーム名、シード番号 |
| 改ページ | 両山では1、2、4、8…ページを指定し、連続するドロー番号の範囲ごとに独立した両山として出力する |

指定ページ数はドローサイズに応じた上限を設け、A4縦の各ページ内へSVGを縮小配置する。画面プレビューでも同じA4縦ページを出力ページ数に合わせて縦に並べる。32ドローを2ページで出力する場合、1ページ目は左山1～8・右山9～16、2ページ目は左山17～24・右山25～32とし、ページ間を接続する線は描画しない。ページ番号 / 総ページ数は各ページのフッター中央に表示する。ブラウザ印刷側で用紙、余白、ヘッダー・フッターを変更した場合は厳密なページ数を保証せず、指定ページ数へ可能な限り収める。

## 7.12 PWA・オフライン利用

### 正規URLとWeb App Manifest

- 正規URLは `https://draw-lab.bamboosato.com/` とする
- Manifestは `/manifest.webmanifest` で配信する
- `name` は `DrawLab`、`short_name` は `DrawLab`、`lang` は `ja` とする
- `id`、`start_url`、`scope` は `/` とする
- `display` は `standalone` とする
- 192px以上および512px以上の実寸アイコンをManifestに登録する。iOS向けに180pxアイコンを追加してよい
- Manifest、Service Worker、アイコンは正規Originから200で配信し、適切なContent-Typeを返す

### Service Workerとキャッシュ境界

- Service Workerは本番ビルドで `/sw.js` として同一Originから登録する
- Service Workerはアプリシェルと公開静的資産の提供だけを担当する
- `index.html` とManifestは更新を検知できる方式で取得し、通信不能時はキャッシュ済みアプリシェルへフォールバックする
- ハッシュ付きJS / CSS、公開アイコン、公開画像などはバージョン付きキャッシュの対象とする
- IndexedDBの大会データ、参加者名簿、生成済みドロー、JSON本文、クリップボード内容、入力途中の状態はCache Storageへ保存しない
- Service Workerから大会データやJSONを外部へ送信しない
- キャッシュ名にはアプリ識別子と世代を含め、世代更新時に不要な旧キャッシュを削除する

### オフライン利用

- 初回のアプリシェル取得とService Worker登録には通信が必要である
- 一度オンラインで正常起動・キャッシュ完了した後は、通信切断中でも一覧表示、入力、生成、IndexedDB保存、JSON入出力、ブラウザ印刷を利用できること
- 初回起動がオフラインでアプリシェル未取得の場合は、空の大会一覧として扱わず、起動できない理由を表示する
- IndexedDB利用不可、保存失敗、容量不足の場合は、既存データを空状態に置き換えず、未保存状態と再試行方法を表示する

### 更新

- 新しいService Workerを検知した場合は、編集中の画面を自動再読み込みしない
- `saving` 中は更新を適用せず、保存完了後にユーザーが更新操作を選択できるようにする
- 更新通知には「更新」「後で」などの明示的な操作を用意する
- 更新失敗時は、現在のアプリとIndexedDBデータを保持し、再試行可能な状態にする

### SPAルーティングと配信

- `/`、`/tournaments`、`/tournaments/new`、`/tournaments/import`、`/leagues`、`/import`、`/tournaments/:id/...` などの画面URLを直接再読み込みしても、正規Originの `index.html` を返すSPAフォールバックをホスティング側に設定する
- `/assets/*`、`/manifest.webmanifest`、`/sw.js`、アイコンなどの静的資産は、SPAフォールバックで `index.html` に置き換えない
- SPAフォールバック未設定による画面URLの404は、PWA受け入れ条件を満たさない

### ホーム起動とインストールガイダンス

- PWAの `start_url`、`id`、`scope` は `/` とし、PWA起動時はホーム画面を表示する
- `display-mode: standalone` を基本にPWA起動状態を判定し、iPhone・iPadでは `navigator.standalone` を補助的に使用してよい
- PWAとして起動中はインストールガイダンスを表示しない
- iPhone・iPadのブラウザ表示では、標準インストール処理を自動実行せず、「インストール方法」から手動追加手順を表示する
- `beforeinstallprompt` が利用できる環境ではイベントを保持し、ユーザーが「インストール」を押したときだけ標準インストールダイアログを表示する。ページ表示を契機に自動表示しない
- 保持したイベントの `prompt()` は1回だけ実行し、`appinstalled` を検知した場合はガイダンスを非表示にする
- 標準インストールダイアログのキャンセルまたはガイダンスの「閉じる」操作後は、初期値として30日間再表示しない
- 非表示時刻は `localStorage` に保存し、利用できない場合は現在のセッション中だけ非表示とする。インストールガイダンスの状態をIndexedDBや既存JSONへ保存しない
- `beforeinstallprompt`、`appinstalled`、PWA起動判定の未対応はエラーにせず、通常のWebアプリ利用を継続する

## 7.13 ホーム画面・共通入口

ホーム画面は、トーナメントとリーグの共通入口として扱う。ホーム画面専用の大会データや状態値は保存しない。

- `/` はホーム画面とする
- トーナメント一覧は `/tournaments`、リーグ一覧は `/leagues` とする
- トーナメント新規作成は `/tournaments/new`、トーナメント情報の復元は `/tournaments/import` とする
- 既存のトーナメント・リーグ編集URL、プレビューURL、リーグ表URLは変更しない
- 既存のトーナメント対戦カードURL `/tournaments/:id/edit/matches` と、リーグ選出画面の旧URL `/leagues/:id/edit/selection` も互換ルートとして維持する。リーグ選出画面の旧URLは参加者入力・選出画面へ置換リダイレクトしてよい
- 旧トーナメント復元URL `/import` は `/tournaments/import` へ `replace` リダイレクトする
- 定義されていない画面URLは `/` へ `replace` リダイレクトする
- `/` の変更により、旧トーナメント一覧を直接開いていたルートURLの表示内容はホーム画面へ変わる。編集・プレビューなどの保存済みURL互換性とは区別して扱う
- URL変更を理由とするIndexedDBのスキーマ変更、保存データの移行、JSON形式の変更、保存済みIDの変更は行わない
- 画面左上のDrawLabロゴから `/` へ遷移できる。サイドバーには「ホーム」を追加しない
- サイドバーの「トーナメント」は `/tournaments` 以下、「リーグ」は `/leagues` 以下でアクティブ表示し、ホーム表示中はどちらもアクティブ表示しない
- ホームの画面タイトルは「トーナメント・リーグ表」とし、画面上のページ名やサイドバーに「ホーム」を表示しない
- トーナメントとリーグの主要機能カードは同じ視覚的優先度で表示し、それぞれ「新規作成」と「一覧を開く」を提供する
- 全体サマリーは既存一覧と同じ状態判定を使用し、トーナメントとリーグはともに「全件・編集中・運用中・完了」を表示する
- 保存領域の読み込み中は0件と確定表示せず、トーナメントとリーグを個別に読み込み中として扱う。片方の保存領域がエラーでも、もう一方の機能は利用可能な状態で表示する
- 保存領域が `ready` でない機能の新規作成操作は無効化し、エラーは空状態と区別して表示する。保存中は既存データを表示したまま保存中であることを示す
- 最近更新した大会はトーナメントとリーグを統合し、`updatedAt` の降順で最大5件を表示する。日時不正・欠損項目は末尾に置き、同値の場合は入力順を維持する
- 最近更新項目には種別、大会名、開催日、状態、最終更新日時、「開く」を表示する。大会名はトーナメントが「無題のトーナメント」、リーグが「無題のリーグ」、開催日未設定は「未設定」とする
- トーナメントの「開く」は、完了済みなら読み取り専用のトーナメント表へ、完了前は基本情報、名簿、オプションのうち最初の未完了ステップへ遷移し、現在のドローが有効な場合はトーナメント表へ遷移する
- リーグの「開く」は、基本情報、名簿・選出、グループ設定、対戦カードのうち最初の未完了ステップへ遷移し、対戦カード確定済みまたは完了済みの場合はリーグ表へ遷移する
- 最近更新項目の遷移先は既存のフロー判定関数を基にした純粋関数で決定し、ホーム画面に別の判定ロジックを持たせない
- 初期版ではホームから「リーグからトーナメントを作成」を直接開始する導線を必須とせず、既存のトーナメント一覧から開始する

## 8. 画面要件

## 8.1 ホーム画面

ホーム画面は `AppShell` 内に表示し、ページの主見出しを `h1` とする。ブラウザタイトルは「トーナメント・リーグ表 | DrawLab」とする。

- 概要文は「トーナメント表とリーグ表を、ブラウザだけで作成・管理できます。」とする
- 上から、ページ見出し、主要機能カード、全体サマリー、最近更新した大会、条件付きPWAインストールガイダンス、データ保存案内の順に配置する
- トーナメントカードとリーグカードは同じ大きさ・情報量・視覚的優先度とする
- PCでは主要機能カードを2列、狭い画面では1列で表示する。320px幅でもページ全体の横スクロールを発生させない
- カード全体をクリック可能にする場合は、カード内ボタンと操作領域を競合させない。初期実装ではボタンとリンクを明示する方式を推奨する
- PWAインストールガイダンスは最近更新項目の下、データ保存案内の上に配置し、主要機能を妨げない補助情報として表示する
- PWAガイダンスやiPhone・iPad向け手順ダイアログは自動表示せず、閉じる操作を提供する
- データ保存案内は「データはこのブラウザ内に保存され、外部へ自動送信されません。対応環境ではオフラインでも利用できます。」を基本文とする
- 読み込み中は `aria-busy` または `role="status"`、保存エラーは `role="alert"` で通知する。アイコンだけで機能を表さず、ロゴリンクにはホーム遷移を示すアクセシブルネームを付ける
- 手順ダイアログはキーボード操作、フォーカストラップ、閉じた後のフォーカス復帰を実装する

## 8.2 トーナメント一覧画面

ローカル保存済みのトーナメントを一覧表示する。

表示項目は以下。

- 大会名
- 種目名
- 開催日
- ドローサイズ
- 最終更新日時
- 編集ボタン
- 複製ボタン
- 削除ボタン

状態は「編集中」「運用中」「完了」で表示する。ドロー未生成または現在の入力と一致しない大会は「編集中」とし、編集ボタンから基本情報画面または最初の未完了画面へ遷移する。有効な生成済みドローがある大会は「運用中」とし、編集ボタンをプルダウンとして表示して保存済みの基本情報、名簿入力、オプション設定、対戦カードの各画面を直接選択できるようにする。完了済みの大会では状態を「完了」と表示し、編集ボタンから読み取り専用のトーナメント表画面へ遷移する。トーナメント表画面の「編集を再開」で確認後に編集状態へ戻せる。トーナメント表は運用中または完了の場合だけ有効とする。初回生成後の有効な変更は自動再生成により運用中を維持し、名簿入力にエラーがある場合は編集中へ戻す。

`開催日` と `最終更新日時` は列見出しをクリックして並び替えできるようにし、見出しの右側へ並び順を示すアイコンを表示する。

- 初期表示は最終更新が新しい順（降順）
- 開催日は近い順（昇順）と遠い順（降順）を切り替える
- 最終更新は新しい順（降順）と古い順（昇順）を切り替える
- 並び替え対象の日付が未設定または不正な場合は末尾に表示する

## 10. 処理フロー

トーナメント生成の基本フローは以下。

```text
1. 基本情報を入力する
2. 名簿を入力する
3. 入力チェックを実行する
4. ドローサイズに合わせてBYEを補完する
5. シード選手を配置する
6. ノーシード選手を配置する
7. チーム・地区の偏りを評価する
8. トーナメント表データを生成する
9. 回戦ごとの対戦カードを生成する
10. 対戦カードで勝敗・備考を入力する
11. 勝者を後続回戦へ反映する
12. SVG/HTMLでプレビュー表示する
13. ローカル保存する
14. PDF出力またはJSONエクスポートを行う
```

## 11. 非機能要件

## 11.1 操作性

- Excelに近い表形式で名簿入力できること
- コピー＆ペーストで大量入力できること
- 入力エラーが分かりやすいこと
- 生成結果をすぐ確認できること

## 11.2 保守性

- 抽選ロジックと描画ロジックを分離すること
- 保存処理とUIを分離すること
- 将来的にクラウド保存へ差し替えやすくすること
- トーナメント生成ロジックは単体テスト可能な純粋関数に近づけること

## 11.3 再現性

- 生成時の乱数シードを保存すること
- 同じ入力と同じ乱数シードで同じ生成結果を再現できること

## 11.4 パフォーマンス

PoCでは128ドローまでを対象とし、通常のPCブラウザでストレスなく生成・表示できること。

目安は以下。

| ドローサイズ | 目安 |
|---|---|
| 32ドロー | 即時表示 |
| 64ドロー | 1秒以内を目標 |
| 128ドロー | 数秒以内を許容 |

## 11.5 セキュリティ・プライバシー

PoCではクラウド保存を行わないため、参加者データは基本的にユーザーのブラウザ内に保存される。

注意点は以下。

- ローカル保存データは同一ブラウザ内に残る
- 共有はPDFまたはJSONファイル経由となる
- JSON共有時には参加者名・所属情報が含まれる
- クラウド保存を導入する場合は、利用規約・プライバシーポリシーを別途整備する

## 11.6 PWA・オフライン・更新

- HTTPSの正規OriginでPWAをインストールできること
- オンラインで一度正常起動した後、通信切断中にアプリシェルを起動できること
- オフライン時も、既存のIndexedDBデータを一覧表示・編集・保存できること
- Cache Storageにユーザー入力、参加者名簿、生成済みドロー、JSON本文を保存しないこと
- Service Workerの更新が、編集中または保存中の画面を自動的に破棄しないこと
- 正規Originとlocalhost・別ホストの保存領域を混同しないこと
- 対応ブラウザ外では、通常のWebアプリとして利用できること。PWAインストール可否をアプリ機能の必須条件にしないこと
- ホーム画面表示のために新しい外部通信、外部API、外部画像を必須としないこと
- ホーム画面の件数・状態・最近更新項目は、既存のトーナメント・リーグ保存データからブラウザ内で算出すること
- トーナメント一覧とリーグ一覧で使用する状態判定をホーム画面で重複実装しないこと
- トーナメントとリーグを横断する表示用ViewModelは、保存処理やReact UIから分離したテスト可能な純粋関数とすること
- ホーム画面追加によって、参加者名や大会情報を外部へ送信しないこと。アクセス解析も追加しないこと

- IndexedDBに保存された全大会を、1つの全大会バックアップJSONとしてエクスポートできる

- 不正JSON、未対応のスキーマ、保存失敗のいずれかが発生した場合、復元前の全大会データが保持される
- ブラウザ印刷でPDF保存できる
- 生成済みドローがあれば、試合結果の入力状況にかかわらずトーナメント表画面から「トーナメントを完了」で完了状態にできる
- 完了済みトーナメントが一覧・ホームで「完了」と表示され、トーナメント表が読み取り専用になる
- 完了済みトーナメント表から確認付きで「編集を再開」でき、結果・備考・組合せを保持する
- 抽選ロジックと描画ロジックが分離されている
- 同じ乱数シードで同じ生成結果を再現できる
- 正規OriginでManifestとService Workerが配信され、PWAとしてインストールできる
- 初回オンライン起動後、通信切断中でもアプリシェルが起動する
- オフライン中もIndexedDBの既存大会を保持し、入力・生成・保存・JSON入出力・印刷ができる
- Service WorkerのCache Storageにユーザーデータが保存されない
- 新バージョン検知時、編集中の内容を保持したまま更新を延期または適用できる

- ホームからトーナメント・リーグの新規作成と一覧表示を開始できる
- トーナメントとリーグのカードが同じ視覚的優先度で表示される

- 保存領域の片方または両方がエラーでも、空状態とエラーを区別して表示できる
- 最近更新項目が両種別を横断して日時降順に並び、最大5件、欠損・不正日時は末尾、同日時は入力順で表示される

- 既存IndexedDB、JSON形式、保存済みIDを変更せず、README・画面仕様・PWA説明文が実装内容と一致する

## 14. 実装上の設計方針

既存VBAの以下は移植しない。

- Excel Ribbon
- CommandBar
- Excelセル結合による描画
- Excel罫線によるトーナメント線描画
- 隠しシートによる設定保存
- Excel PageSetup
- ライセンス処理

WEB版では、以下を独自実装する。

- 名簿データ構造
- シード配置ロジック
- BYE配置ロジック
- チーム・地区偏り回避ロジック
- トーナメント表データモデル
- 対戦カード、勝敗、勝ち上がり状態のデータモデル
- 勝者経路を反映したSVG / HTML描画
- SVG / HTML描画
- ローカル保存
- JSON入出力
- 印刷用レイアウト
- Web App Manifest、Service Worker、静的資産キャッシュ
- PWA更新通知と更新適用制御
- ホスティング側のSPAフォールバック

アプリの中核は、以下のように分離する。

```text
UI
  ↓
入力バリデーション
  ↓
トーナメント生成ロジック
  ↓
トーナメント表データ
  ↓
SVG / HTMLレンダリング
  ↓
PDF出力・保存
```

この分離により、将来的なクラウド保存、共有URL、詳細スコア管理、PDF生成サーバー化に対応しやすくする。

PWAでは、Service Workerをトーナメント生成・保存ロジックから分離する。

```text
React UI / Router
  ├─ TournamentProvider
  │    └─ TournamentRepository ── IndexedDB（大会データの正規保存先）
  ├─ LeagueProvider
  │    └─ LeagueRepository ── IndexedDB（リーグデータの正規保存先）
  ├─ HomeViewModel ── トーナメント・リーグの表示用統合データ
  ├─ JSON入出力サービス ── ファイル入出力
  └─ PWA状態表示・インストール案内 ── Service Worker / ブラウザPWA API

Service Worker
  └─ アプリシェル・公開静的資産のキャッシュのみ
```

Service Workerは `generateDraw()`、`buildBracketViewModel()`、`TournamentRepository` の責務を持たず、Cache StorageとIndexedDBのデータ境界を越えてユーザーデータを扱わない。

ホーム画面は `TournamentProvider` と `LeagueProvider` が提供する既存データを読み取り、件数・状態・最近更新項目を表示用ViewModelへ変換する。ホーム画面用の複製データは保存しない。再開先は既存のフロー判定を利用する純粋関数で決定し、ホーム画面コンポーネントへ判定ロジックを埋め込まない。

PWAインストール案内は、常時表示されるオフライン・更新状態表示とは分離する。`beforeinstallprompt` の保持、`appinstalled` の検知、standalone判定、30日間の非表示管理はフックまたはサービス層で管理し、ホーム画面は表示と操作の委譲だけを担当する。

## 15. Git / 開発運用メモ

- 要件定義書は `docs/requirements.md` を正とする
- 実装時はPoC対象外の機能を安易に追加しない
- 抽選ロジックと描画ロジックは別モジュールとして扱う
