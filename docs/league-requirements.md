# リーグ戦作成Webアプリ 要件定義書

- **プロジェクト名:** リーグ戦作成Webアプリ（Draw Lab連携プロジェクト）
- **文書種別:** リーグ用新規要件定義書
- **バージョン:** 1.0.0（MVP初版・未決定事項あり）
- **作成日:** 2026-08-21
- **対象プラットフォーム:** Web（PC / スマートフォン）
- **関連文書:** `docs/requirements.md`（トーナメント用）

本書は、Draw Labに未実装のリーグ戦作成・運用機能を対象とする。既存のトーナメント要件を変更するものではなく、リーグ機能の要件を独立して定義する。

文中の区分は次のとおりとする。

- **確定:** ユーザー提示のメモおよび追加回答で決定済みの事項
- **提案:** MVPを成立させるための初期案。実装前に確認する
- **未決定:** 要件確定前に運営ルールを決める必要がある事項

---

## 1. プロジェクト概要

### 1.1 背景と目的

大会運営で利用する予選グループリーグを、ブラウザ上で作成・編集・運用できるようにする。将来的には、リーグ順位をDraw Labの決勝トーナメントへ引き渡せる構造にする。

### 1.2 MVPの基本方針

1. 競技ごとの詳細スコアや複雑なタイブレークは扱わず、結果は勝・分・負と自由メモに限定する。
2. 勝点はシステムで集計するが、最終順位は運営者が任意に手動指定できる。
3. 星取表は閲覧用とし、結果入力は対戦カードの一覧で行う。
4. 個人、ダブルス、チームを1つの対戦参加単位として扱う。
5. ローカル保存を基本とし、クラウド・認証・共有URLを前提にしない。

### 1.3 既存トーナメント機能との境界

- リーグは既存の`Tournament`モデルへフィールドを追加せず、独立した`League`モデルとして管理する。
- リーグの順位を決勝トーナメントへ自動マッピングする機能はMVP対象外とする。
- 既存トーナメントの生成ロジック、ドロー、シード、BYEの仕様は本書の対象外とする。

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| リーグ | 1大会分のリーグ戦データ全体 |
| 参加単位 | 対戦を行う単位。個人、ダブルス、チームのいずれか |
| メンバー | 参加単位を構成する個人。個人参加では1名、ダブルスでは2名、チームでは複数名を想定 |
| 選出者 | 定員内に入り、リーグへ参加する参加単位 |
| 補欠 | 定員外だが繰り上げ候補として保持する参加単位 |
| グループ | 予選リーグを分割した対戦単位の集合 |
| 対戦カード | 2つの参加単位と結果・備考を持つ試合データ |
| 勝点 | 勝・分・負の結果に応じて加算する数値 |
| 手動順位 | 運営者が確定させる順位。勝点による自動順位とは別に保持する |

## 3. MVP対象範囲

### 3.1 対象機能

- リーグ基本情報の登録・編集
- 個人、ダブルス、チームの参加単位登録
- 改行区切りテキストの一括貼り付け
- 参加単位の個別追加・編集・削除
- 定員設定
- 定員超過時のランダム抽選
- 選出者と補欠の自動割り当て
- 補欠から選出者への手動繰り上げ
- グループ数または1グループ人数の指定
- 選出者の自動均等グループ分け
- 総当たり方式の対戦カード生成
- 部分当たり方式の対戦カード生成
- グループごとの順位表表示
- 勝点の自動集計
- 勝点設定の大会単位での変更
- 全参加単位を対象とする手動順位指定
- グループごとの星取表表示
- 対戦カード単位の勝・分・負入力
- 対戦カードごとの備考入力
- リーグデータのローカル保存
- リーグデータのJSONエクスポート・インポート

### 3.2 対象外

- ユーザー登録、ログイン、権限管理
- クラウド保存、共有URL、共同編集
- Draw Labトーナメント表への自動連携
- 試合の詳細スコア入力
- セット数、ゲーム数、得失点差の計算
- 競技団体ごとのタイブレーク自動判定
- 試合結果による勝ち上がり自動更新
- リーグと決勝トーナメントの一括大会管理
- ライブ配信、通知、外部連携
- サーバーサイドPDF生成

- 参加者名簿、抽選、グループ分け、試合結果を管理する担当者

## 6. 機能要件

### 6.1 リーグ基本情報（LR-F-001）

リーグ作成時に、次の項目を登録できること。

- 大会名（必須）
- 開催日（任意）
- 会場（任意）
- 種目名（任意）
- 備考（任意）
- 参加単位種別（個人 / ダブルス / チーム）

リーグID、作成日時、更新日時はシステムが付与する。

### 6.2 参加単位登録（LR-F-002）

- 改行区切りのテキストを貼り付けて、参加単位を一括登録できること。
- 個別追加、編集、削除ができること。
- 各参加単位は一意なIDを持つこと。
- 参加単位種別に応じて、表示名およびメンバー情報を保持できること。
- ダブルスは2名のメンバーを登録できること。
- チームは複数名のメンバーを登録できること。
- 参加単位の所属、地区、備考などの補助情報を保持できること。
- 表示名が空の参加単位は選出対象にできないこと。
- 同じ表示名は警告とし、IDが異なる場合は登録を妨げないこと。

### 6.3 定員・選出・補欠（LR-F-003）

- 定員を正の整数で指定できること。
- 定員を超える登録がある場合、選出方法としてランダム抽選を選択できること。
- 抽選結果として、定員数までを選出者、それ以外を補欠として自動分類すること。
- 抽選に使用した乱数シードをリーグデータに保存すること。
- 同じ入力、同じ抽選シード、同じ抽選条件では同じ結果を再現できること。
- 定員以内の場合は、登録済み参加単位を選出者として扱うこと。
- 運営者が選出者と補欠を個別に変更できること。
- 選出者に欠員が発生した場合、運営者が補欠から繰り上げる参加単位を手動指定できること。
- 繰り上げにより定員を超過させないこと。
- 繰り上げ後のグループ・対戦カードを再計算する場合は、結果データへの影響を事前に表示すること。

### 6.4 グループ分け（LR-F-004）

- グループ数指定または1グループ人数指定を選択できること。
- 選出者を自動でグループへ均等に振り分けられること。
- グループごとの人数差は、可能な限り1名以内とすること。
- グループ名は初期値としてA、B、Cなどを付与し、編集可能とすること。
- 運営者が参加単位を別グループへ手動移動できること。
- グループ人数が1名となる設定はエラーとすること。
- グループ分け確定後の参加単位変更は、対戦カード再生成の確認を要求すること。

### 6.5 対戦方式設定（LR-F-005）

対戦方式として次を選択できること。

1. **総当たり**：同一グループ内の全参加単位が、他の全参加単位と1回ずつ対戦する。
2. **部分当たり**：1参加単位あたりの実施試合数を指定し、その条件を満たす対戦カードを生成する。

総当たりでは、グループ人数を`n`とした場合の対戦数を`n × (n - 1) / 2`とする。

部分当たりでは、次を満たすことを基本とする。

- 同一グループ内の同じ組み合わせを重複させない。
- 指定試合数を満たせない場合は、生成を中断して理由を表示する。
- 自動生成した対戦カードの順番を保持する。
- 対戦カード単位で、手動による順番変更を可能にするかは未決定とする。

### 6.6 勝点設定（LR-F-006）

- 勝ち、引き分け、負けに付与する勝点をリーグごとに指定できること。
- 勝点は整数として入力できること。
- 勝点は0以上とすることを提案する。
- 初期値は勝ち3点、引き分け1点、負け0点を提案する。
- 未実施の対戦カードは勝点集計対象外とする。
- 結果を変更・削除した場合、勝点を即時再計算すること。

### 6.7 リーグダッシュボード（LR-F-007）

リーグダッシュボードは、グループ選択と次の3表示を備えること。

- 順位表
- 星取表
- 対戦カード

#### 順位表

少なくとも次を表示すること。

- 順位
- 参加単位名
- 試合数
- 勝数、分数、負数
- 勝点
- 手動順位の状態

自動表示では勝点の降順を基本とする。最終順位は運営者が全参加単位を対象に手動指定できること。

#### 星取表

- 行と列に同一グループの参加単位を表示すること。
- 対角線は対戦対象外として表示すること。
- 勝・分・負・未実施を識別できること。
- 星取表から結果を直接編集できないこと。
- 横幅が画面を超える場合は、ページ全体を崩さず表部分をスクロールできること。

#### 対戦カード

- 試合順、参加単位A、参加単位B、結果、備考を表示すること。
- 結果は未実施、A勝、引き分け、B勝から選択できること。
- 結果入力は、A・Bの表示名と同じ行で行えること。
- 備考を自由入力できること。
- 結果の変更、クリア、備考の編集ができること。
- 保存中、保存済み、保存失敗の状態を表示すること。

### 6.8 手動順位指定（LR-F-008）

- 同率かどうかにかかわらず、運営者が全参加単位の順位を指定できること。
- 順位指定方法は、順位番号入力または参加単位の並べ替えのいずれかとする。採用方式は未決定とする。
- 同一順位の重複、欠番、対象外参加単位がある場合は確定できないことを提案する。
- 手動順位は勝点による自動集計値とは別に保存すること。
- 順位確定前は「未確定」、確定後は「確定」と表示すること。
- 結果を変更した場合、手動順位を維持するか再確認するかは未決定とする。

### 6.9 ローカル保存（LR-F-009）

- リーグの基本情報、参加単位、選出・補欠、グループ、対戦方式、勝点設定、対戦結果、備考、手動順位を保存すること。
- 保存先はブラウザ内のローカルストレージまたはIndexedDBとする。
- 保存はリーグ単位で行い、既存トーナメントデータと混在させないこと。
- 保存処理は画面操作を長時間ブロックしないこと。
- 保存失敗時は入力済みデータを破棄せず、再試行可能な状態にすること。

### 6.10 JSON入出力（LR-F-010）

- リーグ単位でJSONをエクスポートできること。
- JSONにはスキーマバージョン、リーグID、参加単位ID、グループID、対戦カードID、勝点設定、結果、手動順位を含めること。
- JSONインポートは、既存リーグを上書きせず、新しいリーグとして追加することを基本とする。
- インポート時はIDの衝突を避けるため、新しいリーグIDおよび必要な関連IDを発行することを提案する。
- 不正なJSON、必須項目不足、参照先不在のデータはインポートしないこと。
- インポート失敗時に既存リーグを変更しないこと。

## 7. データモデル案

### 7.1 League

```ts
type League = {
  id: string;
  title: string;
  date?: string;
  venue?: string;
  eventName?: string;
  participantType: "individual" | "doubles" | "team";
  capacity: number;
  participants: LeagueParticipant[];
  selection: LeagueSelection;
  groups: LeagueGroup[];
  matchPolicy: LeagueMatchPolicy;
  scoringPolicy: LeagueScoringPolicy;
  matches: LeagueMatch[];
  standings: LeagueStanding[];
  status: "draft" | "scheduled" | "inProgress" | "completed";
  createdAt: string;
  updatedAt: string;
};
```

### 7.2 LeagueParticipant

```ts
type LeagueParticipant = {
  id: string;
  displayName: string;
  participantType: "individual" | "doubles" | "team";
  memberNames: string[];
  team?: string;
  region?: string;
  note?: string;
  selectionStatus: "selected" | "reserve" | "excluded";
};
```

### 7.3 選出・グループ・対戦・順位

```ts
type LeagueSelection = {
  mode: "all" | "random" | "manual";
  randomSeed?: string;
  selectedParticipantIds: string[];
  reserveParticipantIds: string[];
};

type LeagueGroup = {
  id: string;
  name: string;
  participantIds: string[];
};

type LeagueMatchPolicy = {
  mode: "roundRobin" | "partialRoundRobin";
  matchesPerParticipant?: number;
};

type LeagueScoringPolicy = {
  winPoints: number;
  drawPoints: number;
  lossPoints: number;
};

type LeagueMatch = {
  id: string;
  groupId: string;
  order: number;
  participantAId: string;
  participantBId: string;
  result: "unplayed" | "participantAWin" | "draw" | "participantBWin";
  note?: string;
};

type LeagueStanding = {
  groupId: string;
  participantId: string;
  played: number;
  wins: number;
  draws: number;
  losses: number;
  points: number;
  manualRank?: number;
  rankStatus: "unconfirmed" | "confirmed";
};
```

### 7.4 データモデルの設計原則

- 参加単位IDを表示名の代わりに参照し、同名参加単位を区別できるようにする。
- 対戦結果は「参加単位Aから見た勝敗」ではなく、A勝・引き分け・B勝として保存する。
- 対戦カードは結果未入力の状態を保持できるようにする。
- 集計値は再計算可能な派生データとし、元の対戦結果を正とする。
- 手動順位は自動集計結果を上書きせず、別データとして保持する。

## 8. バリデーション要件

### 8.1 エラー

- 大会名が未入力
- 定員が0以下または不正な値
- 選出者数が定員を超過
- 選出者が2名未満のグループを作成
- グループ数が選出者数を超過
- 部分当たりの試合数が1未満
- 部分当たりの試合数が同一グループの他参加単位数以上
- 部分当たりの条件では均等な対戦カードを生成できない
- 対戦カードの参加単位が同一
- 勝点が負数または不正な値
- 対戦結果が許可された値ではない
- 手動順位が重複・欠落・範囲外
- 参照先の参加単位またはグループが存在しない
- JSONスキーマバージョンを処理できない

### 8.2 警告

- 参加単位名が重複している
- 補欠が存在しない状態で選出者に欠員がある
- 結果入力済みのリーグで参加単位・グループ・対戦方式を変更しようとしている
- 手動順位が未確定のままリーグを完了しようとしている
- 未実施の対戦カードが残っている状態で順位を確定しようとしている

## 9. 画面要件

### 9.1 画面一覧

| 画面 | 目的 |
|---|---|
| リーグ一覧 | 保存済みリーグの表示、新規作成、削除、復元 |
| リーグ基本情報 | 大会名、種別、会場などの入力 |
| 参加単位登録 | 個人・ダブルス・チームの登録 |
| 選出・補欠調整 | 定員、抽選、選出者、補欠、繰り上げの管理 |
| グループ・対戦設定 | グループ分け、総当たり・部分当たり、勝点設定 |
| リーグダッシュボード | 順位表、星取表、対戦カードの運用 |
| JSON復元 | リーグJSONの検証と追加インポート |

### 9.2 共通UI

- 現在の作業段階を表示する。
- 入力エラーと警告を区別して表示する。
- 保存状態を表示する。
- 破壊的操作には確認を表示する。
- キーボード操作とスクリーンリーダーで主要操作を実行できること。
- スマートフォンではグループタブと表示タブを横スクロールまたは折り返しで操作できること。
- 結果入力ボタンは、色だけに依存せずテキストまたはARIAラベルで状態を識別できること。

### 9.3 画面遷移と状態

```text
draft
  -> participantsReady
  -> selectionReady
  -> groupsReady
  -> scheduled
  -> inProgress
  -> completed
```

- 必須入力が完了していない段階へは進めないこと。
- 対戦カード生成後に参加単位、グループ、対戦方式を変更する場合は再生成確認を表示すること。
- 結果入力済みの対戦カードを再生成によって失う場合は、変更前のデータを保存または明示的に確認できること。
- `completed`への遷移条件と、完了後の編集可否は未決定とする。

## 10. 非機能要件

### 10.1 プライバシー・保存

- 参加者名、チーム名、備考は、ユーザーの明示操作なしに外部へ送信しないこと。
- リーグ作業にクラウド接続やログインを必須としないこと。
- PWAキャッシュには、参加者名や結果などのユーザーデータを含めないこと。

### 10.2 再現性・整合性

- 抽選結果は乱数シードと選出条件から再現できること。
- 対戦カードID、参加単位ID、グループIDの参照整合性を維持すること。
- 結果入力の保存競合で、直前の入力を静かに失わないこと。

### 10.3 性能

- 典型的な大会規模の登録、グループ分け、対戦カード生成、集計を操作待ち時間なく実行できること。
- グループ内参加者数が増えても、星取表はページ全体のレイアウトを破壊しないこと。

### 10.4 保守性

- リーグの集計・抽選・対戦生成はReactコンポーネントから分離した純粋関数として実装すること。
- UI、ドメインロジック、保存、JSON変換を分離すること。
- `Tournament`と`League`の型・保存処理・画面遷移を混在させないこと。

## 11. テスト設計方針

テストケース作成前に、次の観点を列挙してから詳細化する。各ケースには、何を検証するかという意図を記載する。

### 11.1 機能観点

- 個人、ダブルス、チームの登録
- 定員内登録、定員超過、抽選、補欠化
- 同一シードでの抽選再現性
- 手動による補欠繰り上げ
- グループ数指定、人数指定、均等振り分け
- 総当たりのカード数と重複なし
- 部分当たりの試合数条件
- 勝点設定と結果別集計
- 対戦結果の変更・クリア
- 全参加単位を対象とした手動順位指定

### 11.2 非機能観点

- PC / スマートフォンの表示
- 星取表の横スクロール
- キーボード操作、ARIAラベル、色に依存しない結果表示
- ローカル保存、再読み込み、ブラウザ再起動後の復元
- 保存中の連続入力、非同期保存、保存失敗からの復旧
- ネットワーク不安定時のローカル操作

### 11.3 データ観点

- 参加単位IDによる同名区別
- グループ・対戦カード・順位の参照整合性
- JSONエクスポートとインポートの往復
- 不正JSONの拒否と既存データ非破壊
- 抽選・グループ分け・対戦生成後のデータ保持
- 結果変更時の集計再計算

### 11.4 UI観点

- 各ステップの前提条件と遷移制御
- グループ切り替えと3表示の切り替え
- 結果入力の選択状態と保存状態
- 再生成時の警告・確認表示
- エラーと警告の表示位置・文言・復旧操作

### 11.5 分類

各観点について、次を分けてテストする。

- 正常系
- 異常系
- 境界値
- 状態遷移
- 前提条件が崩れた場合
- 非同期処理・競合・タイミング依存
- 端末・OS・ブラウザ差異

同一実機に対する自動テストの並列実行は行わない。E2Eの実施範囲は変更リスクに応じて選定し、対象・未実施範囲・理由を結果に記載する。

## 12. 受入条件

- リーグを新規作成し、個人・ダブルス・チームの参加単位を登録できる。
- 定員超過時に抽選結果と補欠を確認できる。
- 抽選シードを保持し、同じ条件で同じ選出結果を再現できる。
- 欠員時に運営者が補欠から繰り上げる参加単位を選択できる。
- グループ数またはグループ人数を指定して、選出者をグループ分けできる。
- 総当たりまたは部分当たりの対戦カードを生成できる。
- 対戦カードから勝・分・負を入力できる。
- 勝点設定に従って順位表の勝点が再計算される。
- 星取表は結果を閲覧できるが、結果入力は対戦カードからのみ行う。
- 勝点にかかわらず、運営者が全参加単位の順位を手動指定できる。
- リーグをローカル保存し、再読み込み後も状態を復元できる。
- JSONエクスポートしたリーグを新しいリーグとしてインポートできる。
- 不正な入力・JSONによって既存データが破壊されない。
- 既存のトーナメント作成・保存・JSON入出力に影響を与えない。

## 13. 未決定事項

実装開始前に、次の項目を確定する。

1. 部分当たりで、指定試合数を満たせない場合の扱い（エラー、近似、手動調整）。
2. 部分当たりの対戦相手・試合順の決定方法（乱数、固定順、手動）。
3. ダブルス・チームのメンバー人数上限とメンバー情報の必須範囲。
4. 勝点の入力可能範囲（整数のみか、小数を許可するか）。
5. 手動順位のUI方式（順位番号入力か、並べ替え操作か）。
6. 手動順位の一部未入力を許可するか。
7. 結果入力後に参加単位・グループ・対戦方式を変更した場合の扱い。
8. 補欠繰り上げ時に既存のグループ・対戦結果を保持するか、再生成するか。
9. `completed`確定後の結果・順位編集可否。
10. リーグ一覧を既存トーナメント一覧と同一画面に表示するか、リーグ専用一覧に分けるか。
11. リーグの印刷・PDF出力をMVPに含めるか。
