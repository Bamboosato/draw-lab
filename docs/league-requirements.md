# リーグ戦作成Webアプリ 要件定義書

- **プロジェクト名:** リーグ戦作成Webアプリ（Draw Lab連携プロジェクト）
- **文書種別:** リーグ用新規要件定義書
- **バージョン:** 1.2.1（対応案No.1〜11、リーグ星取表PDF/印刷を確定）
- **作成日:** 2026-08-21
- **更新日:** 2026-08-31
- **対象プラットフォーム:** Web（PC / スマートフォン）
- **関連文書:** `docs/requirements.md`（トーナメント用）

本書は、Draw Labに未実装のリーグ戦作成・運用機能を対象とする。既存のトーナメント要件を変更するものではなく、リーグ機能の要件を独立して定義する。

文中の区分は次のとおりとする。

- **確定:** ユーザー提示のメモおよび追加回答で決定済みの事項
- **提案:** MVPを成立させるための初期案。実装前に確認する
- **未決定:** 要件確定前に運営ルールを決める必要がある事項

---

## 1. プロジェクト概要

### 1.1 背景と目的

大会運営で利用する予選グループリーグを、ブラウザ上で作成・編集・運用できるようにする。将来的には、リーグ順位をDraw Labの決勝トーナメントへ引き渡せる構造にする。

### 1.2 MVPの基本方針

1. 競技ごとの詳細スコアや複雑なタイブレークは扱わず、結果は勝・分・負と自由メモに限定する。
2. 順位は勝点の降順、同点時は星取表の並び順によりシステムで自動計算する。運営者は必要な場合だけ訂正順位を入力でき、入力済みの訂正順位を確定順位として扱う。
3. 星取表は閲覧用とし、結果入力は対戦カードの一覧で行う。
4. 個人、ダブルス、チームを1つの対戦参加単位として扱う。
5. ローカル保存を基本とし、クラウド・認証・共有URLを前提にしない。
6. 星取表は、選択中グループを手書き用の専用レイアウトでブラウザ印刷できるようにする。

### 1.3 既存トーナメント機能との境界

- リーグは既存の`Tournament`モデルへフィールドを追加せず、独立した`League`モデルとして管理する。
- リーグの順位を決勝トーナメントへ自動マッピングする機能はMVP対象外とする。
- 既存トーナメントの生成ロジック、ドロー、シード、BYEの仕様は本書の対象外とする。

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| リーグ | 1大会分のリーグ戦データ全体 |
| 参加単位 | 対戦を行う単位。個人、ダブルス、チームのいずれか |
| メンバー | 参加単位を構成する個人。個人参加では1名、ダブルスでは2名、チームでは1名以上 |
| 選出者 | 定員内に入り、リーグへ参加する参加単位 |
| 補欠 | 定員外だが繰り上げ候補として保持する参加単位 |
| グループ | 予選リーグを分割した対戦単位の集合 |
| 対戦カード | 2つの参加単位と結果・備考を持つ試合データ |
| 勝点 | 勝・分・負の結果に応じて加算する数値 |
| 訂正順位 | 運営者が必要な場合だけ入力する順位。勝点による自動順位とは別に保持し、入力済みの場合は確定順位として扱う |

## 3. MVP対象範囲

### 3.1 対象機能

- リーグ基本情報の登録・編集
- 個人、ダブルス、チームの参加単位登録
- 改行区切りテキストの一括貼り付け
- 参加単位の個別追加・編集・削除
- 定員設定
- 定員超過時のランダム抽選
- 選出者と補欠の自動割り当て
- チェック操作による選出者と補欠の切り替え
- グループ数または1グループ人数の指定
- 選出者の自動均等グループ分け
- グループ内の全組み合わせによる候補カード生成
- 候補カードの有効／無効選択
- グループごとの順位表表示
- 勝点の自動集計
- 勝点設定の大会単位での変更
- 自動順位の表示と、必要な参加単位への訂正順位入力
- グループごとの星取表表示
- 選択中グループの星取表のPDF保存・印刷（ブラウザ印刷）
- 対戦カード単位の勝・分・負入力
- 対戦カードごとの備考入力
- 保存済みリーグ一覧の表示、開催日・最終更新による並び替え
- リーグの複製・削除・個別JSON出力
- リーグデータのローカル保存
- 個別リーグJSONの追加インポート
- 全リーグバックアップJSONの出力と確認付き全置換復元

### 3.2 対象外

- ユーザー登録、ログイン、権限管理
- クラウド保存、共有URL、共同編集
- Draw Labトーナメント表への自動連携
- 試合の詳細スコア入力
- セット数、ゲーム数、得失点差の計算
- 競技団体ごとのタイブレーク自動判定
- 試合結果による勝ち上がり自動更新
- リーグと決勝トーナメントの一括大会管理
- ライブ配信、通知、外部連携
- サーバーサイドPDF生成

## 6. 機能要件

### 6.1 リーグ基本情報（LR-F-001）

リーグ作成時に、次の項目を登録できること。

- 大会名（任意）
- 開催日（任意）
- 会場（任意）
- 種目名（任意）
- 備考（任意）
- 画面上の種目区分（シングル / ダブルス / チーム）

リーグID、作成日時、更新日時はシステムが付与する。

### 6.2 参加単位登録（LR-F-002）

- 名簿入力画面の初期表示では、基本情報で設定した定員と同数の空行を表示すること。
- 空行は入力済み参加者数・選出者数には算入せず、参加者名を入力した行から実参加者として扱うこと。
- 改行区切りのテキストを貼り付けて、参加単位を一括登録できること。
- 貼り付け列は実際の入力項目順とし、シングルは「選手名・所属・地区・備考」、ダブルスは「ペア名・選手名1・選手名2・所属・地区・備考」、チームは「チーム名・メンバー（/区切り）・所属・地区・備考」とすること。
- 貼り付け時は、既存の入力済み参加単位を保持し、保存済みの空行へ順に取り込み、余った行を末尾へ追加すること。
- 個別追加、編集、削除ができること。
- 各参加単位は一意なIDを持つこと。
- 種目区分に応じて、表示名およびメンバー情報を保持できること。
- 対戦カード確定前に参加単位の追加・削除・表示名・メンバー・所属・地区・備考などの更新を行った場合は、グループ分け、対戦カード、有効カード確定状態、順位集計をリセットし、再設定を求めること。
- グループまたは対戦カード設定が存在する状態で参加単位を変更する場合は、リセット内容を説明する確認ダイアログを表示すること。キャンセル時は変更を反映せず、確認時にリセットと参加単位の変更を反映すること。
- 対戦カード確定後は、参加単位の変更を禁止し、対戦カード画面で確定解除した後に変更できること。確定解除時に結果入力済みの場合は、確認後にすべての対戦結果をリセットすること。
- 参加単位の追加・削除・更新によるリセットでは、勝点設定を保持すること。
- ダブルスは、空欄でないメンバー名をちょうど2名登録すること。
- チームは、空欄でないメンバー名を1名以上登録すること。MVPでは固定の上限を設けないこと。
- 参加単位の所属、地区、備考などの補助情報を保持できること。
- 表示名が空の参加単位は選出対象にできないこと。
- 同じ表示名は警告とし、IDが異なる場合は登録を妨げないこと。

### 6.3 定員・選出・補欠（LR-F-003）

- 定員を正の整数で指定できること。
- 選出は名簿入力画面上のチェックボックスによる手動指定を基本とすること。
- 名簿入力画面では、入力済みの全参加者を一覧表示し、表の最左列に選出チェックボックスを配置すること。
- チェックありを選出者、チェックなしを補欠として扱うこと。チェックなしの行全体（各セルと入力欄）は薄いグレーで表示すること。
- 初期状態では、定員内の登録済み参加者を選出者としてチェック済みにすること。定員を超える場合は、超過状態を表示して運営者がチェックを外して調整すること。
- 名簿入力画面の上部操作に`自動選出`ボタンを配置し、`行追加`ボタンの左側に置くこと。
- `自動選出`は、入力済み参加者から定員分をランダムに選出し、既存のチェック状態を破棄して選出結果へ置き換えること。入力済み参加者が定員未満の場合は全員を選出すること。
- 抽選に使用した乱数シードをリーグデータに保存すること。
- 同じ入力、同じ抽選シード、同じ抽選条件では同じ結果を再現できること。
- チェック状態の変更により、選出者と補欠を相互に変更できること。別の補欠一覧、`補欠にする`、`繰り上げる`操作は設けないこと。
- 選出者数が1名未満または定員を超える場合は、次のステップへ進めないこと。
- グループまたは対戦カード設定が存在する状態で選出者を変更する場合は、リセット確認を表示し、確認後にグループ分けと対戦カードを再構成すること。
- 対戦カード確定後は選出チェックボックスを操作不可とすること。

### 6.4 グループ分け（LR-F-004）

- グループ数指定または1グループ人数指定を選択できること。
- 選出者を自動でグループへ均等に振り分けられること。
- グループごとの人数差は、可能な限り1名以内とすること。
- 自動振り分けでは、同じ所属または地区の参加単位が同じグループへ集中しないよう、可能な範囲で分散すること。
- 所属・地区の分散と人数均等を同時に満たせない場合は、グループ人数差1以内を優先し、属性の重複が少ない配置を選ぶこと。
- 同じ入力とグループ数では、自動振り分け結果を再現できること。
- グループ名は初期値としてA、B、Cなどを付与し、編集可能とすること。
- 運営者が参加単位を別グループへ手動移動できること。
- グループ人数が1名となる設定はエラーとすること。
- 対戦カード確定後の参加単位変更は、対戦カードの確定解除を要求すること。
- グループ設定画面は、グループ、No.、選手名、所属、地区、備考、操作の一覧で表示すること。
- 一覧はグループの昇順、グループ内は名簿入力と同じNo.の昇順で表示すること。
- 操作列に参加単位のグループ変更ボタンを表示すること。
- 地区と備考は、名簿入力画面と同じ詳細列の開閉操作で表示・非表示を切り替えられること。

### 6.5 対戦カード設定（LR-F-005）

対戦方式の選択は設けず、同一グループ内の全組み合わせを候補カードとして生成すること。

- グループ人数を`n`とした場合、対戦候補数は`n × (n - 1) / 2`とする。
- 各候補カードの初期状態は有効とする。
- 運営者が各候補カードを「有効」または「無効」に切り替えられること。
- 対戦カード確定前は、有効／無効を変更できること。
- 対戦カード確定後は、有効／無効を変更できないこと。
- 対戦カード画面に`対戦カードを確定`と`確定解除`を配置し、確定している場合だけリーグ表へ遷移できること。
- `確定解除`時に結果入力済みカードが1件でもある場合は確認ダイアログを表示し、確認後はすべての対戦結果を`unplayed`へリセットして未確定に戻すこと。結果未入力の場合は確認なしで未確定に戻すこと。
- 無効化したカードの結果・備考は削除せず保持し、無効中は試合数・勝敗数・勝点の集計対象外とすること。
- 有効カードの確定後に対戦カード候補自体を失わないこと。
- 候補カード確定時に、グループごとの候補数・有効数・無効数と、参加単位ごとの有効試合数を表示すること。
- MVPでは、有効カードの試合順を運営者が手動変更できないこと。生成された試合順を保持すること。

### 6.6 勝点設定（LR-F-006）

- 勝ち、引き分け、負けに付与する勝点をリーグごとに指定できること。
- 勝点は整数で、0以上100以下の範囲で入力できること。
- 初期値は勝ち3点、引き分け1点、負け0点とすること。
- 勝点設定はグループ振り分け・対戦カード設定とは分離し、リーグ一覧の各リーグ行にある「その他の操作」から編集できること。
- 未実施の対戦カードは勝点集計対象外とする。
- 結果を変更・削除した場合、勝点を即時再計算すること。

### 6.7 リーグダッシュボード（LR-F-007）

リーグダッシュボードは、グループ選択と次の3表示を備えること。

- 順位表
- 星取表
- 対戦カード

#### 順位表

少なくとも次を表示すること。

- 順位
- 参加単位名
- 試合数
- 勝数、分数、負数
- 勝点
- 訂正順位
- 星取表の縦方向と順位表の参加者列は、ダブルスをペア名と氏名の読み取り専用表示とし、星取表の横方向の列見出しはペア名だけを表示すること。

自動順位は勝点の降順とし、勝点が同じ場合は星取表の並び順が早い参加単位を上位とする。順位表には自動順位と訂正順位を分けて表示し、訂正順位が入力されている参加単位は、その値を確定順位として扱うこと。

#### 星取表

- 行と列に同一グループの参加単位を表示すること。
- 対角線は対戦対象外として表示すること。
- 勝・分・負・未実施を識別できること。
- 星取表から結果を直接編集できないこと。
- 横幅が画面を超える場合は、ページ全体を崩さず表部分をスクロールできること。

#### 星取表のPDF保存・印刷

- リーグ表画面の`リーグを完了`の右側に`PDF/印刷`を配置すること。
- `PDF/印刷`は選択中グループの星取表だけを対象とし、画面表示用のUIをそのまま印刷しないこと。
- 用紙はA4縦とし、ブラウザ印刷を利用すること。サーバーサイドでPDFを生成しないこと。
- グループ内の参加単位数をNとし、Nが1〜8の場合は1ページにN行×N列を配置すること。
- Nが9〜16の場合は、1ページ目にN行×8列、2ページ目にN行×（N-8）列を配置すること。
- 17以上のグループはMVPの印刷対象外とし、`PDF/印刷`を実行できないこと。
- 行・列の参加者はグループ内の名簿No.順とし、参加者名を印刷すること。ダブルス・チームは表示名とメンバー名を識別できること。
- 対角セルには左上から右下へ引く対角線（`＼`）を出力し、それ以外のセルは空欄とすること。
- 結果、勝点、画面上の`勝`・`負`・`分`・`未`・`無`は印刷しないこと。
- 結果を手書きできるよう、結果セルの高さは3行分以上を確保すること。
- PDF保存時の既定ファイル名は`大会名_リーグ表-グループA`の形式とすること。
- Nが9〜16の場合、2ページ目以降の結果列の幅は1ページ目の結果列と同じ幅とし、列数の差は右側の余白で吸収すること。

#### 対戦カード

- 試合順、参加単位A、参加単位B、結果、備考を表示すること。
- 結果は未実施、A勝、引き分け、B勝から選択できること。
- 結果入力は、A・Bの表示名と同じ行で行えること。
- 備考を自由入力できること。
- 結果の変更、クリア、備考の編集ができること。
- 保存中、保存済み、保存失敗の状態を表示すること。

### 6.8 順位・訂正順位（LR-F-008）

- 順位表の項目は、参加者、試合、勝、分、負、勝点、順位、訂正とすること。
- `順位`は勝点の降順で自動計算し、勝点が同じ場合は星取表の並び順が早い参加単位を上位とすること。
- `訂正`は初期状態では読み取り専用とし、順位表右上の`訂正`ボタンで編集モードへ切り替えられること。保存後は読み取り専用へ戻ること。
- 訂正順位は必要な参加単位だけ入力でき、未入力を許可すること。入力値はグループ内の順位範囲で、重複しないこと。
- 訂正順位は自動順位とは別に保存し、入力済みの場合は確定順位として扱うこと。
- 訂正順位が未入力でも、リーグは自動順位を利用して運用・完了できること。
- 試合結果を変更した場合は自動順位を再計算するが、入力済みの訂正順位は自動消去しないこと。

### 6.9 ローカル保存（LR-F-009）

- リーグの基本情報、参加単位、選出・補欠、グループ、候補カードの有効状態、勝点設定、対戦結果、備考、自動順位、訂正順位を保存すること。
- 保存先はブラウザ内のローカルストレージまたはIndexedDBとする。
- 保存はリーグ単位で行い、既存トーナメントデータと混在させないこと。
- 保存処理は画面操作を長時間ブロックしないこと。
- 保存失敗時は入力済みデータを破棄せず、再試行可能な状態にすること。

### 6.10 JSON入出力（LR-F-010）

- リーグ単位でJSONをエクスポートできること。
- JSONにはスキーマバージョン、リーグID、参加単位ID、グループID、対戦カードID、勝点設定、結果、自動順位、訂正順位を含めること。
- JSONインポートは、個別リーグを既存リーグへ上書きせず、新しいリーグとして追加することを基本とする。
- 個別リーグのインポート時は、IDの衝突を避けるため、新しいリーグIDおよび必要な関連IDを発行すること。
- 保存済みの全リーグを1つのバックアップJSONとしてエクスポートできること。
- 全リーグバックアップJSONを復元する場合は、現在の全リーグをバックアップ内容へ置き換えること。
- 全リーグの置換復元は、実行前に対象件数と既存データが削除されることを確認ダイアログで表示すること。
- 全リーグバックアップが0件の場合も復元を許可し、現在の全リーグを削除することを明示すること。
- 全リーグバックアップの復元時は、バックアップ内のリーグIDおよび関連IDを保持すること。
- 不正なJSON、必須項目不足、参照先不在のデータはインポートしないこと。
- インポート失敗時に既存リーグを変更しないこと。
- リーグを複製する場合は、基本情報、参加単位、選出・補欠、グループ、勝点設定を引き継ぎ、新しいリーグIDおよび関連IDを発行すること。
- 複製後の対戦カードは候補カードとして保持し、`matchSelectionStatus`を`pending`、全カードの`isValid`を`true`として未確定状態に戻すこと。
- 複製後の対戦結果と備考は空（`unplayed`・空欄）とし、勝点・試合数・勝敗数・自動順位・訂正順位は初期状態へ戻すこと。
- 複製元のリーグは変更せず、複製後のリーグを新規データとして保存すること。

## 7. データモデル案

### 7.1 League

```ts
type League = {
  id: string;
  title: string;
  date?: string;
  venue?: string;
  eventName?: string;
  participantType: "individual" | "doubles" | "team";
  capacity: number;
  participants: LeagueParticipant[];
  selection: LeagueSelection;
  groups: LeagueGroup[];
  scoringPolicy: LeagueScoringPolicy;
  matches: LeagueMatch[];
  standings: LeagueStanding[];
  status: "draft" | "scheduled" | "inProgress" | "completed";
  matchSelectionStatus: "pending" | "confirmed";
  createdAt: string;
  updatedAt: string;
};
```

### 7.2 LeagueParticipant

```ts
type LeagueParticipant = {
  id: string;
  displayName: string;
  participantType: "individual" | "doubles" | "team";
  memberNames: string[];
  team?: string;
  region?: string;
  note?: string;
  selectionStatus: "selected" | "reserve" | "excluded";
};
```

### 7.3 選出・グループ・対戦・順位

```ts
type LeagueSelection = {
  mode: "all" | "random" | "manual";
  randomSeed?: string;
  selectedParticipantIds: string[];
  reserveParticipantIds: string[];
};

type LeagueGroup = {
  id: string;
  name: string;
  participantIds: string[];
};

type LeagueScoringPolicy = {
  winPoints: number;
  drawPoints: number;
  lossPoints: number;
};

type LeagueMatch = {
  id: string;
  groupId: string;
  order: number;
  participantAId: string;
  participantBId: string;
  isValid: boolean;
  result: "unplayed" | "participantAWin" | "draw" | "participantBWin";
  note?: string;
};

type LeagueStanding = {
  groupId: string;
  participantId: string;
  played: number;
  wins: number;
  draws: number;
  losses: number;
  points: number;
  rank?: number;
  manualRank?: number;
  rankStatus: "unconfirmed" | "confirmed";
};
```

### 7.4 データモデルの設計原則

- 参加単位IDを表示名の代わりに参照し、同名参加単位を区別できるようにする。
- 対戦結果は「参加単位Aから見た勝敗」ではなく、A勝・引き分け・B勝として保存する。
- 対戦カードは結果未入力の状態を保持できるようにする。
- 集計値は再計算可能な派生データとし、元の対戦結果を正とする。
- `rank`は勝点と星取表の並び順から導出する自動順位として保持し、`manualRank`は画面上の訂正順位として自動集計結果とは別に保持する。

## 8. バリデーション要件

### 8.1 エラー

- 定員が0以下または不正な値
- 選出者数が定員を超過
- 選出者が2名未満のグループを作成
- グループ数が選出者数を超過
- 対戦カードの参加単位が同一
- ダブルスのメンバー数が2名でない
- チームのメンバー数が1名未満
- 勝点が整数でない、または0〜100の範囲外
- 対戦結果が許可された値ではない
- 訂正順位が重複・範囲外
- 対戦カード確定後に参加単位またはグループを変更しようとしている
- 対戦カード確定後に選出チェックを変更しようとしている
- 参照先の参加単位またはグループが存在しない
- JSONスキーマバージョンを処理できない

### 8.2 警告

- 参加単位名が重複している
- 補欠が存在しない状態で選出者に欠員がある
- 訂正順位の入力値が不正なまま保存またはリーグを完了しようとしている
- 未実施の対戦カードが残っている状態で順位を確定しようとしている

## 9. 画面要件

### 9.1 画面一覧

| 画面 | 目的 |
|---|---|
| リーグ一覧 | 既存トーナメント一覧とは分離した、保存済みリーグの表示、新規作成、編集、複製、削除、勝点設定、個別JSON出力、全リーグバックアップ、個別／全件復元 |
| リーグ基本情報 | 大会名、種別、会場などの入力 |
| 名簿入力・選出 | 参加者登録、定員、選出者、補欠、自動選出の管理 |
| グループ設定 | グループ分け、所属・地区・備考の確認、候補カード作成前のグループ変更 |
| リーグダッシュボード | 順位表、星取表、対戦カードの運用 |
| JSON復元 | 個別リーグの追加インポート、または全リーグバックアップの全置換復元 |

### 9.2 共通UI

- 現在の作業段階を表示する。
- 入力エラーと警告を区別して表示する。
- 保存状態を表示する。
- 破壊的操作には確認を表示する。
- 名簿入力画面はトーナメントの名簿入力画面と同じく、上部操作、概要帯、参加者一覧、TSV/CSV貼り付け、下部ナビゲーションの順で配置すること。
- 名簿入力画面では、`自動選出`、`行追加`、`空行削除`、`入力チェック`、`一覧`、`戻る`、`次へ`の操作を提供すること。`自動選出`は`行追加`の左側に配置すること。
- 名簿一覧の最左列に`選出`チェックボックスを配置し、チェックありを選出者、チェックなしを補欠として扱うこと。チェックなしの行全体（各セルと入力欄）は薄いグレーで表示すること。
- 画面上の参加者名列・貼り付け操作は「選手名／ペア名／チーム名」「TSV/CSV貼り付け」「貼り付けを取り込み」と表示し、`参加単位`は要件・モデル上の用語として扱うこと。一覧の見出し・件数表示は置かず、表パネルを直接表示すること。
- 参加者入力概要は「参加者数」「選択済み」「定員」を固定幅で左寄せに並べ、「選択済み」には現在チェックされている選出者数を表示すること。入力チェック後にエラーがある場合だけ右端へエラー文言を表示し、名簿入力画面に独立したエラーカードを挿入しないこと。
- 参加者一覧の表パネル外側に、追加の見出し・件数表示・カード枠を設けないこと。
- 一覧画面はトーナメント一覧と同じページ見出し、概要帯、表パネル、追加アクションメニューの構造を使用する。
- 一覧の概要帯は「全リーグ」「編集中」「運用中」「完了」の順に固定幅で左寄せに並べ、5列目は空欄とする。スマートフォン幅ではトーナメント一覧と同じレスポンシブ表示へ切り替える。
- 一覧の列は、大会名、種目、開催日、定員、状態、最終更新、アクションとする。
- 開催日と最終更新は、トーナメント一覧と同じ昇順・降順の切り替え操作を提供する。
- 一覧上部の追加アクションメニューに、全リーグバックアップおよび個別／全件復元への導線を配置する。個別リーグの出力は各行のその他の操作メニューへ配置する。
- 各リーグ行のアクションは、編集、リーグ表、その他の操作メニュー（複製、出力、削除）で構成する。
- キーボード操作とスクリーンリーダーで主要操作を実行できること。
- スマートフォンではグループタブと表示タブを横スクロールまたは折り返しで操作できること。
- 結果入力ボタンは、色だけに依存せずテキストまたはARIAラベルで状態を識別できること。
- リーグの印刷では、画面表示用UIと印刷用文書を分離し、`.no-print`による操作UIの除外と、印刷対象の意味的な構造を確保すること。

### 9.3 画面遷移と状態

```text
draft
  -> participantsReady
  -> selectionReady
  -> groupsReady
  -> scheduled
  -> inProgress
  -> completed
```

- 必須入力が完了していない段階へは進めないこと。
- グループ内の全組み合わせを候補カードとして作成し、初期状態は全カード有効とすること。対戦カード確定時に`scheduled`へ進めること。
- 有効カード確定前は、再編集操作によって有効／無効を変更できること。
- 有効カード確定後は、有効／無効を変更せず、既存の有効状態と集計を保持すること。
- 無効カードに保持された結果・備考は、無効中は集計せず保持すること。
- 対戦カード確定前は、参加単位またはグループの変更に伴うカード再生成を確認付きで許可すること。名簿入力画面の編集はフォーカス離脱時に変更を確定し、既存のグループまたは対戦カードがある場合は、リセット確認後に反映すること。初期表示およびフォーカス離脱だけではエラーを表示せず、`入力チェック`または`次へ`操作後に表示すること。
- 対戦カード確定後は、参加単位の追加・削除、選出チェック、グループ変更などの構造変更を禁止すること。変更する場合は、対戦カードの確定解除を行い、結果入力済みなら確認後にすべての結果をリセットすること。
- 結果と備考は結果入力後も編集できること。リーグ表の参加者表示（ペア名・氏名を含む）は読み取り専用とすること。結果変更時は勝点を再計算し、手動順位は保持したうえで再確認を促すこと。
- `completed`へは全順位の入力完了後に遷移できること。`completed`中は読み取り専用とすること。
- `completed`を再開する場合は運営者の確認を取り、`inProgress`へ戻すこと。結果、備考、手動順位、有効カード状態は保持すること。

## 10. 非機能要件

### 10.1 プライバシー・保存

- 参加者名、チーム名、備考は、ユーザーの明示操作なしに外部へ送信しないこと。
- リーグ作業にクラウド接続やログインを必須としないこと。
- PWAキャッシュには、参加者名や結果などのユーザーデータを含めないこと。

### 10.2 再現性・整合性

- 抽選結果は乱数シードと選出条件から再現できること。
- 対戦カードID、参加単位ID、グループIDの参照整合性を維持すること。
- 結果入力の保存競合で、直前の入力を静かに失わないこと。

### 10.3 性能

- 典型的な大会規模の登録、グループ分け、対戦カード生成、集計を操作待ち時間なく実行できること。
- グループ内参加者数が増えても、星取表はページ全体のレイアウトを破壊しないこと。
- 星取表のPDF/印刷は、N=1、8、9、16の境界でページ分割とセル高を満たすこと。

### 10.4 保守性

- リーグの集計・抽選・対戦生成はReactコンポーネントから分離した純粋関数として実装すること。
- UI、ドメインロジック、保存、JSON変換を分離すること。
- `Tournament`と`League`の型・保存処理・画面遷移を混在させないこと。

## 12. 受入条件

- リーグを新規作成し、個人・ダブルス・チームの参加単位を登録できる。
- ダブルスはメンバー2名、チームはメンバー1名以上で登録できる。
- 定員超過時に自動選出結果と補欠を確認できる。
- 抽選シードを保持し、同じ条件で同じ選出結果を再現できる。
- 名簿一覧のチェック操作で選出者と補欠を切り替えられる。
- 対戦カード確定前は、選出チェック変更後にグループ・対戦カードを再構成できる。確定後は現在のリーグでの選出変更が拒否される。
- グループ数またはグループ人数を指定して、選出者をグループ分けできる。
- 同一グループ内の全組み合わせによる候補カードを生成できる。
- 候補カードから有効カードを選択・確定できる。
- 有効カード確定前は有効／無効を変更でき、確定後は変更できない。
- 候補カードの試合順は生成順で固定され、MVPでは手動変更できない。
- 対戦カード確定後は、有効／無効を変更できず、既存の状態と集計を保持する。
- 無効カードの結果・備考を保持し、無効中は集計対象外とする。
- 対戦カードから勝・分・負を入力できる。
- 勝点設定に従って順位表の勝点が再計算される。
- 勝点を0〜100の整数で指定でき、初期値が勝ち3・引き分け1・負け0である。
- 星取表は結果を閲覧できるが、結果入力は対戦カードからのみ行う。結果セルは勝ちを「勝」、負けを「負」、引き分けを「分」、未実施を「未」、無効カードを「無」と表示する。
- 勝点にかかわらず、運営者が全参加単位の順位を手動指定できる。
- 手動順位は順位番号入力で指定でき、作業中の一部未入力を許可し、完了時には全順位の入力を要求する。
- 対戦カード確定後も結果・備考を編集でき、リーグ表の参加者表示は読み取り専用とし、構造変更は拒否される。結果変更後は手動順位を保持したまま再確認を促す。
- `completed`のリーグは読み取り専用で表示され、確認後に`inProgress`へ再開できる。
- リーグをローカル保存し、再読み込み後も状態を復元できる。
- JSONエクスポートした個別リーグを新しいリーグとしてインポートできる。
- 全リーグバックアップを出力し、確認付きで現在の全リーグを置換復元できる。
- 不正な入力・JSONによって既存データが破壊されない。
- リーグ一覧が既存トーナメント一覧と分離され、既存`AppShell`のUI方針に沿って表示される。
- リーグ一覧の表示項目、並び替え、追加アクション、行アクションがトーナメント一覧と同じ操作密度で提供される。
- リーグ表の選択中グループについて、専用レイアウトの星取表をA4縦でPDF保存・印刷できる。N=1〜8は1ページ、N=9〜16は8列と残り列に分割し、対角線以外は空欄で、結果セルは3行分以上の高さを持つ。
- 既存のトーナメント作成・保存・JSON入出力に影響を与えない。

## 13. 対応案No.1〜11の確定事項

| No. | 確定事項 |
|---:|---|
| 1 | 対戦方式は選択せず、同一グループ内の全組み合わせを候補カードとして生成する。初期状態は全カード有効とし、有効／無効は対戦カード画面で調整する。 |

| 4 | 勝点は0〜100の整数とし、初期値は勝ち3・引き分け1・負け0とする。 |

| 8 | 欠員発生時は名簿の選出チェックを変更する。対戦カード確定前は再構成を許可し、確定後は現在のリーグで禁止する。 |
